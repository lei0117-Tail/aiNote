# 四个核心执行型 Agent 对照：`sisyphus`、`sisyphus-junior`、`hephaestus`、`atlas`

这篇文档把 oh-my-openagent / omo-opencode 里最容易混淆的 4 个核心执行型 agent 放到同一张图里比较。它们都能“做事”，但角色层级完全不同：

- `sisyphus` 是主线程里的全能执行主力。
- `sisyphus-junior` 是被委派出去的通用子任务执行器。
- `hephaestus` 是更偏深度实现和工程落地的 specialist。
- `atlas` 是偏任务编排和多 agent 协作的 orchestrator。

## 1. 先看一句话定位

| Agent | 一句话定位 |
|---|---|
| `sisyphus` | 主会话里的全能型主执行 agent |
| `sisyphus-junior` | `task/category` 拉起的通用子任务 worker |
| `hephaestus` | 深度实现导向的 autonomous engineer |
| `atlas` | 任务编排导向的 master orchestrator |

这 4 个 agent 的差异不在于“谁更强”，而在于“谁处在哪一层”。

## 2. 第一层差异：谁是主线程，谁是子线程

### 2.1 `sisyphus` 和 `atlas` 都是 primary

从源码上看：

- `sisyphus` 是默认主力 agent 之一，承担主会话里的复杂任务推进。
- `atlas` 也是 `primary`，但它的 primary 不是为了自己干完所有活，而是为了调度别的 agent。

所以这两个虽然都在顶层可直接选用，但职责完全不同：

- `sisyphus` 是主执行者。
- `atlas` 是主编排者。

### 2.2 `sisyphus-junior` 是明确的 subagent

[`sisyphus-junior/AGENTS.md`](/Users/liulei/aiS/oh-my-openagent/packages/omo-opencode/src/agents/sisyphus-junior/AGENTS.md) 讲得非常直白：

- 它是 “category-spawned executor”
- mode 是 `subagent`
- 由 `delegate-task` 在 category 路由时拉起

也就是说它不是给用户当默认顶层 agent 选的，而是给系统在拆任务时拿来当统一 worker 的。

### 2.3 `hephaestus` 虽是 primary，但更像“专门工种”

[`hephaestus/agent.ts`](/Users/liulei/aiS/oh-my-openagent/packages/omo-opencode/src/agents/hephaestus/agent.ts) 里把它描述成：

- `Autonomous Deep Worker`
- `goal-oriented execution`
- `completes tasks end-to-end`

所以它虽也是 primary，但不是“总控型 primary”，而是“重执行型 primary”。

## 3. 第二层差异：谁偏执行，谁偏编排

### 3.1 `sisyphus`：主会话里的通用执行脑

`sisyphus` 的特点不是某个单一专长，而是覆盖面最大：

- 能读代码
- 能改代码
- 能调工具
- 能决定什么时候拆任务
- 能结合 skills / categories / hooks / tool guards 持续推进

它像系统里的默认“总干事”。大部分复杂任务如果不特别指定，最后都能由它接住。

### 3.2 `sisyphus-junior`：被拆出去的通用 worker

它和 `sisyphus` 不是简单的“弱化版/缩小版”关系，更准确地说是执行上下文不同：

- `sisyphus` 在主线程里，负责全局推进和决策。
- `sisyphus-junior` 在子线程里，负责把某一块明确任务干完。

它的关键特征是：

- 常由 `task(category=...)` 隐式调用；
- 自己不承担顶层 orchestration；
- 按 category、skill、模型配置临时扮演一个领域执行者。

所以它更像“通用子任务内核”，不是前台主角。

### 3.3 `hephaestus`：更强烈的“深挖然后落实现”

`hephaestus` 的 prompt 元数据和描述都很鲜明：

- 深度探索后再实现
- 端到端完成任务
- 适合复杂 multi-file implementation
- 不适合需要大量 orchestration 的场景

这一点在它的 `avoidWhen` 里甚至写明了：

- 当任务需要多 agent 编排时，应该用 `Atlas`

所以 `hephaestus` 的边界很清楚：

- 它不是为了协调团队；
- 它是为了盯住一个复杂工程目标狠狠干到底。

### 3.4 `atlas`：先拆、先派、先协调

[`atlas/agent.ts`](/Users/liulei/aiS/oh-my-openagent/packages/omo-opencode/src/agents/atlas/agent.ts) 里最关键的一句话是：

- `Orchestrates work via task() to complete ALL tasks in a todo list until fully done.`

这句话其实已经定义了它的本质：

- Atlas 自己不是主要交付实现的人；
- 它的核心能力是把一个 todo list 或多步骤工作拆成子任务，然后通过 `task()` 让合适的 agent 去做。

所以如果说 `hephaestus` 像高级工程师，`atlas` 更像 tech lead / dispatcher。

## 4. 第三层差异：它们和 `task` 的关系不同

### 4.1 `atlas` 对 `task` 是强依赖

Atlas 的存在几乎和 `task` 绑在一起。没有 `task`，它的 orchestrator 身份就很难成立，因为它的核心价值就是：

- 看任务列表
- 决定拆分
- 调用子 agent
- 协调收敛

所以 Atlas 是 `task` 生态里的“上层大脑”。

### 4.2 `sisyphus` 会用 `task`，但不被 `task` 定义

Sisyphus 作为主执行 agent，当然也会把部分工作委派出去，但它的身份不依赖 `task` 才成立。即使不拆任务，它仍然能直接完成很多工作。

所以：

- `task` 是它的一个能力；
- 不是它的定义中心。

### 4.3 `sisyphus-junior` 是 `task` 生态的直接产物

这点最明确。

category 路由大多会落到 `sisyphus-junior`，意味着它的主要出场场景并不是“用户手动选择”，而是系统通过 `task` 把它拉起来。

所以它和 `task` 的关系不是“会使用”，而是“由其生成”。

### 4.4 `hephaestus` 和 `task` 是互补关系

Hephaestus 并不以 orchestrator 为主，但在复杂场景下可以成为被委派的深度实现者。

所以：

- `task` 可以把某些复杂实现工作交给 Hephaestus；
- Hephaestus 自己的价值仍然在实现执行本身，而不是分派。

## 5. 第四层差异：模型和 prompt 适配策略也不同

### 5.1 `sisyphus`：变体最多，适配最广

从已有源码分析可以看出，Sisyphus 对不同模型家族有大量 prompt 变体和动态拼装逻辑：

- Claude
- GPT-5.4 / GPT-5.5
- Gemini
- Kimi K2.x

它是整个系统里模型适配最重的 agent，因为它要承担默认主力位。

### 5.2 `sisyphus-junior`：同样多变体，但定位更聚焦

`sisyphus-junior` 也有自己的模型变体和 fallback chain，但这些变体不是为了当顶层万能 agent，而是为了让 category worker 在不同模型下都能稳定完成明确子任务。

重点是“稳定做完子任务”，不是“承担系统总控复杂性”。

### 5.3 `hephaestus`：强模型约束

[`hephaestus/agent.ts`](/Users/liulei/aiS/oh-my-openagent/packages/omo-opencode/src/agents/hephaestus/agent.ts) 里写得很硬：

- 只支持 GPT-5.3 Codex、GPT-5.4、GPT-5.5

这说明 Hephaestus 的人格和方法论是为特定模型家族校准的，不追求横向兼容所有模型。

也因此它表现出更强的 specialist 气质。

### 5.4 `atlas`：更看重编排 prompt，而不是实现 prompt

Atlas 也有多模型 prompt variant，但它的 prompt 注入重点不是如何写代码，而是：

- category section
- agent selection section
- decision matrix
- skills section
- category-skills delegation guide

换句话说，Atlas 的 prompt 核心是“如何做调度决策”，不是“如何直接做实现”。

## 6. 直接给一张高密度对照表

| 维度 | `sisyphus` | `sisyphus-junior` | `hephaestus` | `atlas` |
|---|---|---|---|---|
| 主定位 | 全能主执行 agent | 通用子任务执行器 | 深度实现 specialist | 多 agent 编排 orchestrator |
| mode | `primary` | `subagent` | `primary` | `primary` |
| 典型入口 | 主会话直接选用 | `task(category=...)` 间接拉起 | 需要强实现导向时直接选或被委派 | 多步骤/todo list/团队协作时直接选 |
| 是否依赖 `task` 才成立 | 否 | 是，强相关 | 否 | 是，强相关 |
| 最强能力 | 端到端推进复杂任务 | 承接明确子任务 | 深挖后落实现 | 拆分、派发、收敛 |
| 更像谁 | 全能 senior IC | worker/executor | 深度工程师 | tech lead / dispatcher |
| 适合什么 | 大多数复杂但可直接推进的任务 | category 子任务、明确外包块 | 多文件复杂实现 | 任务列表、并行协作、系统编排 |
| 不最适合什么 | 纯 orchestration-first 场景 | 顶层总控 | 需要大量多 agent 协调 | 需要自己重度写实现的单任务 |

## 7. 最实用的理解方式

如果把整个系统想成一个小团队，可以这样看：

- `sisyphus`：默认顶在前面的主力工程师。
- `sisyphus-junior`：被拆出去做明确子任务的执行同学。
- `hephaestus`：特别能啃复杂实现的资深工程师。
- `atlas`：负责拆解、派工、追踪完成度的组长。

这个比喻和源码结构其实非常一致，因为：

- Atlas 的 prompt 明显在教它如何选人派工；
- Hephaestus 的 prompt 明显在教它如何深度推进工程实现；
- Sisyphus 负责兜底和大多数默认执行；
- Sisyphus-Junior 则承载 category 驱动的统一 worker 角色。

## 8. 一个最容易记住的结论

不要把这四个 agent 理解成“四个并列功能菜单”。

更准确的理解是：

- `sisyphus` 负责主线程执行；
- `sisyphus-junior` 负责被委派出的通用子线程；
- `hephaestus` 负责重实现型执行；
- `atlas` 负责高层编排。

也就是说，它们不是同一维度上的替代品，而是同一套 agent OS 里不同层级、不同职责的角色。
