# Atlas 与 Hephaestus 源码对照

## 1. 为什么把这两个放在一起看

`Atlas` 和 `Hephaestus` 都是核心 `primary` agent，但它们在系统里的职责完全不同：

- `Atlas`：偏计划推进和清单闭环
- `Hephaestus`：偏深度自主执行

把它们放在一起看，正好能帮助理解 `oh-my-openagent` 并不是“多个同类 agent 并存”，而是“多个不同工作模式的主力角色并存”。

## 2. Atlas：计划推进器

### 2.1 入口

`Atlas` 的实现入口在 [atlas/agent.ts](/Users/liulei/aiS/oh-my-openagent/packages/omo-opencode/src/agents/atlas/agent.ts:118)。

它的 `createAtlasAgent(ctx)` 接收的是 `OrchestratorContext`，而不是简单的模型字符串。这一点很重要，因为它说明 `Atlas` 从一开始就是按“需要吃运行时上下文”的 orchestrator 设计的。

上下文包括：

- `model`
- `availableAgents`
- `availableSkills`
- `userCategories`

### 2.2 Prompt 资产来源

`Atlas` 的 prompt 不是写在 TypeScript 里的大字符串，而是主要来自 `prompts-core` 里的 markdown 资产，再做运行时注入。[atlas/agent.ts](/Users/liulei/aiS/oh-my-openagent/packages/omo-opencode/src/agents/atlas/agent.ts:15)

路由逻辑：

- `Claude Opus 4.7` -> `opus-4-7.md`
- `GPT family` -> `gpt.md`
- `Gemini family` -> `gemini.md`
- `Kimi K2.7` -> `kimi-k2-7.md`
- `Kimi K2.x` -> `kimi.md`
- 默认 -> `default.md`

这说明 `Atlas` 也有模型变体，但它不像 `Sisyphus` 那样把大量策略直接塞在 TypeScript 里，而是更依赖 `prompts-core` 的静态 prompt 资源。

### 2.3 运行时注入

`Atlas` 最核心的源码点在 [atlas/agent.ts](/Users/liulei/aiS/oh-my-openagent/packages/omo-opencode/src/agents/atlas/agent.ts:78) 的 `buildDynamicOrchestratorPrompt()`。

这里会生成：

- `categorySection`
- `agentSection`
- `decisionMatrix`
- `skillsSection`
- `categorySkillsGuide`

然后把这些内容注入到 markdown prompt 的占位符里：

- `{CATEGORY_SECTION}`
- `{AGENT_SECTION}`
- `{DECISION_MATRIX}`
- `{SKILLS_SECTION}`
- `{{CATEGORY_SKILLS_DELEGATION_GUIDE}}`

所以 `Atlas` 的核心机制不是“完全动态拼字符串”，而是“静态 prompt 模板 + 少量关键动态插槽”。

### 2.4 prompt section builder

[atlas/prompt-section-builder.ts](/Users/liulei/aiS/oh-my-openagent/packages/omo-opencode/src/agents/atlas/prompt-section-builder.ts:17) 专门负责这几个动态插槽的内容。

它的特点是：

- 很强调 `category` 和 `agent` 二选一
- 很强调 `load_skills=[...]` 不能随便空着
- 通过 `decision matrix` 明确什么时候该用 category，什么时候该用 agent

这说明 `Atlas` 的主要工作不是“自己深想”，而是“把任务正确分发出去，并保证分发参数完整”。

## 3. Hephaestus：自主深度执行工

### 3.1 入口

`Hephaestus` 的实现入口在 [hephaestus/agent.ts](/Users/liulei/aiS/oh-my-openagent/packages/omo-opencode/src/agents/hephaestus/agent.ts:131)。

和 `Atlas` 相比，它更像 `Sisyphus`：

- 通过工厂函数生成完整 prompt
- 根据模型路由到不同 prompt builder
- 直接在 TypeScript 里拼装出 `AgentConfig`

### 3.2 模型限制

`Hephaestus` 的一个非常重要的特点，是它不是开放给所有模型的。[hephaestus/agent.ts](/Users/liulei/aiS/oh-my-openagent/packages/omo-opencode/src/agents/hephaestus/agent.ts:40)

它只支持：

- `gpt-5.3-codex`
- `gpt-5.4`
- `gpt-5.5`

如果模型不在这个范围内，会直接抛 `UnsupportedHephaestusModelError`。

这说明项目对 `Hephaestus` 的定位非常明确：它是 GPT/Codex 路线的深度执行工，而不是通用 orchestration shell。

### 3.3 动态 prompt 构造

`buildDynamicHephaestusPrompt()` 会根据模型路由到：

- `gpt-5-5`
- `gpt-5-4`
- `gpt`

然后再统一加上 `buildAgentIdentitySection("Hephaestus", ...)`。[hephaestus/agent.ts](/Users/liulei/aiS/oh-my-openagent/packages/omo-opencode/src/agents/hephaestus/agent.ts:81)

这个结构和 `Sisyphus` 很像，但功能导向不同：

- `Sisyphus` 的 prompt 核心是 orchestration policy
- `Hephaestus` 的 prompt 核心是 deep execution discipline

### 3.4 Config 特征

最终生成的 `AgentConfig` 有几个明显特征：

- `maxTokens: 32000`
- `reasoningEffort: "medium"`
- `call_omo_agent: "deny"`
- 叠加 frontier tool schema permission

尤其是 `call_omo_agent: "deny"` 很关键，它说明 `Hephaestus` 并不是再往下继续递归调度一堆 agent 的总控，而是一个更专注于“拿到目标后自己推进”的 worker。

## 4. 两者最本质的区别

我觉得 `Atlas` 和 `Hephaestus` 的最本质区别是：

### 4.1 Atlas 关注的是“任务网络”

它在源码里持续关心：

- 有哪些 category
- 有哪些 skills
- 有哪些 agents
- 怎么选分发路径
- todo list 怎么逐项闭环

### 4.2 Hephaestus 关注的是“任务本体”

它在源码里持续关心：

- 模型是否适合做深度执行
- 当前 prompt 是否足够支持自主推进
- 如何在不靠大量 orchestrator 参与的情况下完成任务

## 5. 和 Sisyphus 的相对位置

如果把三个核心 agent 放一起：

- `Sisyphus`：总调度器
- `Atlas`：清单推进器
- `Hephaestus`：深度执行工

可以把它们理解成三种不同的“主工作模式”：

1. `Sisyphus` 负责判断、分流、协调。
2. `Atlas` 负责沿计划清单推完所有项。
3. `Hephaestus` 负责拿下一个复杂而明确的深度实施目标。

## 6. 结构层面的差异

从源码组织方式上看：

### 6.1 Atlas 更偏“模板 + 注入”

- 静态 markdown prompt 在 `prompts-core`
- TypeScript 负责 runtime injections
- prompt-section-builder 负责局部动态片段

### 6.2 Hephaestus 更偏“工厂 + 代码生成 prompt”

- TypeScript 中有多套 prompt builder
- 工厂根据模型直接选 builder
- 最终直接产出完整 prompt 字符串

这也说明这两个 agent 的维护风格不同：

- `Atlas` 更适合把行为契约沉淀成稳定模板
- `Hephaestus` 更适合在代码里细调 GPT 家族特性

## 7. 什么时候看 Atlas，什么时候看 Hephaestus

如果你后面继续读源码：

- 想理解“任务怎么被拆成 category/skills/agent 的参数化分发” → 优先看 `Atlas`
- 想理解“一个深度 worker 为什么被限制在 GPT/Codex 路线，以及它如何构建自己的执行 prompt” → 优先看 `Hephaestus`

## 8. 一句话总结

`Atlas` 是把计划变成可执行任务网络的推进器，`Hephaestus` 是把复杂目标变成完成结果的深度执行工。
