# Sisyphus Prompt 变体源码对照

## 1. 这份文档看什么

这份文档专门对比 `Sisyphus` 的不同 prompt 变体实现，回答三个问题：

1. 为什么 `Sisyphus` 要针对不同模型族维护多套 prompt
2. 各变体各自在防什么失败模式
3. 哪些规则是全变体共享的，哪些是模型专属补丁

对照入口在 [sisyphus-agent-factory.ts](/Users/liulei/aiS/oh-my-openagent/packages/omo-opencode/src/agents/sisyphus-agent-factory.ts:47)，它明确按模型路由到不同 prompt builder，而不是所有模型共用一份 system prompt。

## 2. 总体判断

从源码上看，`Sisyphus` 的 prompt 体系不是“换个措辞而已”，而是在为不同模型的典型失误模式打补丁。

大致可以这样概括：

- `default / Claude generic`：通用 orchestrator 基线模板
- `GPT-5.4`：高结构化、强 output contract、强执行回路
- `GPT-5.5`：长篇 orchestration contract，强调身份、委派、验证、端到端交付
- `Gemini`：不是完整主模板，而是一套强纠偏 overlay
- `Claude Opus 4.7`：压制过度探索，强化字面遵循和并行调用
- `Claude Opus 4.8 / Fable 5`：在 4.7 基础上进一步抑制过度叙述和过度发问
- `Kimi K2.x`：利用其 RL 训练出的意图推断和 token economy，同时避免重复征税式验证

换句话说，这一套不是“提示词工程炫技”，而是运行时兼容层的一部分。

工厂路由来自 [sisyphus-agent-factory.ts](/Users/liulei/aiS/oh-my-openagent/packages/omo-opencode/src/agents/sisyphus-agent-factory.ts:47)：

- `claude-opus-4-7` -> `buildClaudeOpus47SisyphusPrompt`
- 其他模型 -> fallback prompt

这张路由表本身已经透露出一个设计原则：作者把 prompt 视作“模型适配器”的一部分，而不是稳定不变的业务文案。

## 4. 共享骨架：所有变体都围绕 orchestrator 展开

虽然每个变体细节差很多，但有几个核心点几乎是一致的：

- 都把 `Sisyphus` 定位成 orchestrator，而不是默认实现者。
- 都保留 intent gate。
- 都强调 explore/librarian/oracle/category delegation。
- 都强调先调查、后行动。
- 都强调验证，尤其是 `lsp_diagnostics`、测试和结果核查。
- 都通过动态 sections 注入 agents、skills、categories、tool display。

这些共享逻辑大部分来自动态 builder 层：

- [dynamic-agent-core-sections.ts](/Users/liulei/aiS/oh-my-openagent/packages/omo-opencode/src/agents/dynamic-agent-core-sections.ts:26)
- [dynamic-agent-policy-sections.ts](/Users/liulei/aiS/oh-my-openagent/packages/omo-opencode/src/agents/dynamic-agent-policy-sections.ts:7)
- [dynamic-agent-category-skills-guide.ts](/Users/liulei/aiS/oh-my-openagent/packages/omo-opencode/src/agents/dynamic-agent-category-skills-guide.ts:48)

所以变体之间真正变化的，是“如何把这些共有原则翻译成某个模型最能吃进去的约束格式”。

## 5. `default.ts`：通用基线模板

[default.ts](/Users/liulei/aiS/oh-my-openagent/packages/omo-opencode/src/agents/sisyphus/default.ts:138) 是基线版 prompt builder。它的特点是：

- 用比较完整的 prose 结构组织规则
- 有强烈的 task/todo 管理要求
- 有显式的 intent verbalization
- 有清楚的 delegation check
- 把 tools / explore / librarian / oracle / category+skills guide 全都拼进来

这一版更像“面向 Claude 和泛化模型的标准 orchestrator 说明书”。它假设模型需要完整规则，但还不至于像 Gemini 那样需要反复纠偏。

## 6. `gpt-5-4.ts`：8-block 高结构化变体

[gpt-5-4.ts](/Users/liulei/aiS/oh-my-openagent/packages/omo-opencode/src/agents/sisyphus/gpt-5-4.ts:1) 的文件头已经把设计思路写得非常直白：

- 8-block architecture
- XML 标签和命名锚点
- 强 output contract
- verification loops
- dependency checks
- completeness contract

这说明作者对 GPT-5.4 的判断是：

- 它遵循结构化指令的效果更好
- 它需要被明确提醒去“think first”
- 它可能过于字面，因此要加 intent inference 层

这版更像一份“严格流程机”的 prompt，重点不是灌很多人格内容，而是把行动循环写成可执行协议。

## 7. `gpt-5-5.ts`：长篇 orchestration contract

[gpt-5-5.ts](/Users/liulei/aiS/oh-my-openagent/packages/omo-opencode/src/agents/sisyphus/gpt-5-5.ts:45) 和 5.4 最大的不同，不是结构更多，而是“治理文本”更完整。

它明显强化了这些方面：

- 身份与角色定义
- 并行化要求
- delegation philosophy
- session continuity
- exploration discipline
- autonomy and persistence
- Oracle consultation

这版像是在把 “Sisyphus should behave like a high-discipline tech lead” 写成一份长期行为契约。

相比 5.4，它不只是强调结构化流程，还更强调：

- 你是 orchestrator，不是 implementer
- 你必须监督交付，而不是只发指令
- 你必须把 delegation、verification、manual QA 一起闭环

所以可以把它理解成“结构化 GPT prompt”向“行为契约式 GPT prompt”的演进。

## 8. `gemini.ts`：纠偏覆盖层，不是主模板

[gemini.ts](/Users/liulei/aiS/oh-my-openagent/packages/omo-opencode/src/agents/sisyphus/gemini.ts:1) 很特别，它不是完整地重写一套主 prompt，而是若干 overlay section。

文件头明确指出 Gemini 的典型失败模式：

- 跳过工具调用，靠内部推理
- 不愿委派，喜欢自己做
- 没验证就宣称完成
- 把约束当建议
- 跳过 intent gate
- 把 investigation 误当 implementation

因此 Gemini 的补丁几乎全是“强制纠偏”：

- `buildGeminiToolMandate()`
- `buildGeminiToolGuide()`
- `buildGeminiToolCallExamples()`
- `buildGeminiDelegationOverride()`
- `buildGeminiVerificationOverride()`
- `buildGeminiIntentGateEnforcement()`

这很说明问题：作者认为 Gemini 的主要问题不是“不会理解业务”，而是“过于乐观、过于自作主张、过少调用工具”。

## 9. `claude-opus-4-7.ts`：抑制过度探索

[claude-opus-4-7.ts](/Users/liulei/aiS/oh-my-openagent/packages/omo-opencode/src/agents/sisyphus/claude-opus-4-7.ts:1) 的头注释也写得很清楚：

- literal following
- bounded exploration/thinking
- parallel tool calls re-enabled
- direct tone

也就是说，作者对 Opus 4.7 的判断是：

- 它会比较字面地吃 prompt
- 它容易探索过久、思考过久
- 所以要明确告诉它“sufficient context > complete context”

这版的关键词是“收束”。相比 default，它更强调：

- 不要再多开一轮搜索
- 不要在已经足够正确时继续验证
- 要更直接、更短、更能行动

## 10. `claude-opus-4-8.ts`：在 4.7 基础上再压制“多嘴和多问”

[claude-opus-4-8.ts](/Users/liulei/aiS/oh-my-openagent/packages/omo-opencode/src/agents/sisyphus/claude-opus-4-8.ts:1) 继承了 4.7 的大部分骨架，但额外补了两个非常有意思的问题：

- `SILENCE DEFAULT`
- `SMALL-DECISION AUTONOMY`
- `CAPABILITY UNDER-REACH`

也就是作者认为 Opus 4.8：

- 比 4.7 更爱写过程性叙述
- 更容易在小事上犹豫和发问
- 有时明明有能力也不主动触发工具或 delegation

因此 4.8 版比 4.7 多了更强的：

- 少讲废话
- 小决定自己拍板
- 触发器一旦命中就立刻动用能力

这是一种很典型的“同模型家族内微调 prompt”思路。

## 11. `claude-fable-5.ts`：沿 4.8 方向继续推

[claude-fable-5.ts](/Users/liulei/aiS/oh-my-openagent/packages/omo-opencode/src/agents/sisyphus/claude-fable-5.ts:1) 基本延续了 4.8 的方向，只是把能力层级提得更高。

文件里明确说：

- 它是比 Opus 更高一级的模型
- 但能力更强不等于可以“做得更多”
- 一样要抑制过度探索、过度发问、能力 under-reach

这很有代表性：作者不是因为模型更强，就把 prompt 放松；相反，越强的模型越要在边界上钉死，以避免它用“更强能力”越界行动。

## 12. `kimi-k2-6.ts`：利用 RL 优势，同时防止双重征税

[kimi-k2-6.ts](/Users/liulei/aiS/oh-my-openagent/packages/omo-opencode/src/agents/sisyphus/kimi-k2-6.ts:1) 是所有变体里最“模型训练感知”的一个。

它的头注释明确提到：

- K2.x 有 Toggle RL 和 GRM
- 它本来就有较强 intent inference
- 如果再套一层过重的 Claude 式重复验证，会导致 double-tax

所以这版的设计重点是：

- `re_entry_rule`：已经决定过的事情不要重复 verbalize
- `exploration_budget`：探索有明确止损
- `tiered verification loop`：验证按任务级别分层，不是所有任务都走最重 QA
- `token_economy`：强调省词，但不牺牲真正必要的验证

这说明作者对 Kimi 的态度不是“给它更少约束”，而是“给它更精确的约束，避免把它本来擅长的地方又人为拽慢”。

## 13. 一个简化对照表

| 变体 | 主要问题判断 | 主要补丁方向 |
|---|---|---|
| `default` | 需要通用 orchestrator 基线 | 完整规则、完整委派与验证逻辑 |
| `gpt-5.4` | 适合高度结构化合同式 prompt | 8-block、XML、依赖/验证/完整性契约 |
| `gpt-5.5` | 适合长篇行为契约 | orchestration identity、delegation philosophy、manual QA |
| `gemini` | 过度乐观、少工具、少委派 | 强制工具、强制验证、强制 intent gate |
| `opus-4.7` | 容易过度探索，偏字面 | bounded exploration、直接语气、并行工具 |
| `opus-4.8` | 更爱叙述、更爱问小问题、能力触发不足 | silence default、小决定自治、触发命中即用 |
| `fable-5` | 能力强，但也会过度探索/过度发问 | 沿 4.8 思路强化边界 |
| `kimi-k2.x` | 有 RL 意图推断，但容易被重复验证拖慢 | re-entry、分层验证、token economy |

## 14. 从这些变体里能看出什么架构思想

我觉得这里最值得注意的不是某个 prompt 本身，而是背后的架构思想：

- prompt 是运行时适配层，不是静态文本资源
- 模型差异被当作工程问题处理，而不是“同一个 prompt 应该都行”
- 失败模式是通过源码显式建模的
- `Sisyphus` 真正承载的是 orchestration policy，而不只是说话风格

这也是为什么 `Sisyphus` 在整个仓库里最值得细读。它几乎把：

- agent 编排
- 动态 prompt
- 工具治理
- 委派哲学
- 验证标准
- 模型适配

这些系统级问题都汇总到了一个点上。
