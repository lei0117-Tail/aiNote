# oh-my-openagent 内置 Agent 分析

## 1. 总览

OpenCode 侧一共内置 11 个 agent，定义总表在 [packages/omo-opencode/src/agents/AGENTS.md](/Users/liulei/aiS/oh-my-openagent/packages/omo-opencode/src/agents/AGENTS.md:16)。它们不是平铺的 11 个“人格 prompt”，而是一套分工明确的多角色系统。

最核心的区分有两个：

- `primary`：尊重用户在 UI 中选择的模型。
- `subagent`：忽略 UI 模型，走自己的 fallback 链。

这个划分在 [packages/omo-opencode/src/agents/AGENTS.md](/Users/liulei/aiS/oh-my-openagent/packages/omo-opencode/src/agents/AGENTS.md:104) 里有清晰定义。

## 2. 注册与构建方式

大多数 agent 都通过 [builtin-agents.ts](/Users/liulei/aiS/oh-my-openagent/packages/omo-opencode/src/agents/builtin-agents.ts:32) 中的 `agentSources` 注册，然后由 `createBuiltinAgents()` 结合配置、模型可用性、skills、categories 和 overrides 决定是否真正启用。[builtin-agents.ts](/Users/liulei/aiS/oh-my-openagent/packages/omo-opencode/src/agents/builtin-agents.ts:61)

这里有两个关键点：

- `Sisyphus`、`Hephaestus`、`Atlas` 不是简单地直接放进结果，而是走各自的 `maybeCreate...Config` 包装逻辑。
- `Prometheus` 是特例，不在 `agentSources` 里，单独通过 [prometheus-agent-config-builder.ts](/Users/liulei/aiS/oh-my-openagent/packages/omo-opencode/src/plugin-handlers/prometheus-agent-config-builder.ts:33) 构建。

所以从实现上看，agent 体系分成两层：

1. 原始 agent factory，负责生成某个 agent 的基础配置。
2. 条件工厂层，负责根据当前环境决定这个 agent 该不该出现、用什么模型、带什么限制。

## 3. 角色分组

理解这 11 个 agent，最有效的方式不是逐个背名字，而是按职责分组。

### 3.1 主控型 agent

- `Sisyphus`
- `Hephaestus`
- `Atlas`
- `Prometheus`

### 3.2 专长型 subagent

- `Oracle`
- `Librarian`
- `Explore`
- `Multimodal-Looker`
- `Metis`
- `Momus`
- `Sisyphus-Junior`

## 4. 四个主控型 agent

### 4.1 Sisyphus

`Sisyphus` 是整个系统的主 orchestrator。它的职责不是亲自做所有事，而是理解任务、规划、调用合适的 agent 和工具，并持续推进任务完成。[packages/omo-opencode/src/agents/AGENTS.md](/Users/liulei/aiS/oh-my-openagent/packages/omo-opencode/src/agents/AGENTS.md:22)

它的几个特点：

- `mode = primary`
- 默认模型偏强，且有较长 fallback 链
- 带较高 thinking budget
- prompt 是动态拼装的，会注入 agent 表、category 表和 skills 指南

它的 prompt 不是固定文案，而是由动态 prompt builder 拼起来的，这在 [packages/omo-opencode/src/agents/AGENTS.md](/Users/liulei/aiS/oh-my-openagent/packages/omo-opencode/src/agents/AGENTS.md:116) 有说明。也就是说，`Sisyphus` 本身承担了“总调度器 + 运行时上下文汇总器”的双重角色。

### 4.2 Hephaestus

`Hephaestus` 是自主深度执行工，更像“拿到目标就自己往下做”的工程 agent，而不是协调者。[packages/omo-opencode/src/agents/hephaestus/AGENTS.md](/Users/liulei/aiS/oh-my-openagent/packages/omo-opencode/src/agents/hephaestus/AGENTS.md:10)

关键特征：

- `mode = primary`
- 依赖 OpenAI-compatible provider
- 强调不要信 subagent 自报结果，必须验证
- 倾向并行地让 explore/librarian 在后台帮自己搜集信息

如果说 `Sisyphus` 是“总包工头”，那 `Hephaestus` 更像“资深施工队长”。

### 4.3 Atlas

`Atlas` 是 todo/checkbox 驱动的 orchestrator，强调“按计划把每个框都勾完”。[packages/omo-opencode/src/agents/atlas/AGENTS.md](/Users/liulei/aiS/oh-my-openagent/packages/omo-opencode/src/agents/atlas/AGENTS.md:10)

它和 `Sisyphus` 的区别不只是 prompt 风格不同，而是推进模型不同：

- `Sisyphus` 偏总体任务编排。
- `Atlas` 偏任务清单推进。

`Atlas` 的重要行为约束包括：

- 默认并行派发任务，只有命名依赖才串行
- 派发后要更新 checkbox，再读回确认，再继续下一步
- 不会在计划步骤之间反复向用户请求批准

这些约束写在 [atlas/AGENTS.md](/Users/liulei/aiS/oh-my-openagent/packages/omo-opencode/src/agents/atlas/AGENTS.md:53)。

### 4.4 Prometheus

`Prometheus` 是战略规划 agent，专门用于 interview-mode 或深度规划场景。[packages/omo-opencode/src/agents/prometheus/AGENTS.md](/Users/liulei/aiS/oh-my-openagent/packages/omo-opencode/src/agents/prometheus/AGENTS.md:10)

它有几个非常鲜明的架构特征：

- 它是一个“薄适配器”，真正的 prompt 资产在 `prompts-core`。
- 规划机制依赖 path-backed 的 `ulw-plan` skill。
- 它只负责调研、规划、生成 `.md` 计划文档，不负责实现。
- 它受到强 hook 约束，只能改 `.md` 文件。

所以 `Prometheus` 更像是“计划控制面”，而不是通用 agent。[packages/omo-opencode/src/agents/prometheus/AGENTS.md](/Users/liulei/aiS/oh-my-openagent/packages/omo-opencode/src/agents/prometheus/AGENTS.md:35)

## 5. 七个专长型 subagent

### 5.1 Oracle

只读顾问。适合做判断、解释、评估，但不负责修改代码或继续调度别的 agent。[packages/omo-opencode/src/agents/AGENTS.md](/Users/liulei/aiS/oh-my-openagent/packages/omo-opencode/src/agents/AGENTS.md:24)

### 5.2 Librarian

偏外部文档和资料搜索，像一个研究助理。它也被限制为只读，不直接落地修改。[packages/omo-opencode/src/agents/AGENTS.md](/Users/liulei/aiS/oh-my-openagent/packages/omo-opencode/src/agents/AGENTS.md:25)

### 5.3 Explore

偏代码库内部的上下文搜索，类似一个更有语义约束的 grep/探索 agent。[packages/omo-opencode/src/agents/AGENTS.md](/Users/liulei/aiS/oh-my-openagent/packages/omo-opencode/src/agents/AGENTS.md:26)

### 5.4 Multimodal-Looker

处理图片、PDF、视觉内容。这个 agent 的限制最严格之一，基本是“只保留读能力”。[packages/omo-opencode/src/agents/AGENTS.md](/Users/liulei/aiS/oh-my-openagent/packages/omo-opencode/src/agents/AGENTS.md:27)

### 5.5 Metis

偏正式规划前的预分析顾问，帮助在开始行动前理解问题、摸清路径。[packages/omo-opencode/src/agents/AGENTS.md](/Users/liulei/aiS/oh-my-openagent/packages/omo-opencode/src/agents/AGENTS.md:28)

### 5.6 Momus

计划 reviewer，作用更像“挑刺的审稿人”。当系统需要有人专门质疑方案、找漏洞时，它很合适。[packages/omo-opencode/src/agents/AGENTS.md](/Users/liulei/aiS/oh-my-openagent/packages/omo-opencode/src/agents/AGENTS.md:29)

### 5.7 Sisyphus-Junior

这是 category 路由出来的执行型小工。它不像 `Sisyphus` 那样总控，也不像 `Hephaestus` 那样偏大型自主施工，而是接收一个更聚焦的子任务后直接执行。[packages/omo-opencode/src/agents/sisyphus-junior/AGENTS.md](/Users/liulei/aiS/oh-my-openagent/packages/omo-opencode/src/agents/sisyphus-junior/AGENTS.md:10)

它的重要特征有：

- `mode = subagent`
- 默认模型是 `claude-sonnet-4-6`
- 不能继续使用 `task` 分发
- 对 GPT 模型还会额外限制 `apply_patch`
- 允许 `call_omo_agent`，方便局部再调只读探索 agent

所以它比较像“带一点调研能力的基层执行工”。

## 6. Tool restriction 是架构，不只是权限表

这些 agent 的差异并不只体现在 prompt 文案上，更体现在工具限制上。[packages/omo-opencode/src/agents/AGENTS.md](/Users/liulei/aiS/oh-my-openagent/packages/omo-opencode/src/agents/AGENTS.md:34)

比如：

- `Oracle/Librarian/Explore` 禁止 `write/edit/task/call_omo_agent`
- `Multimodal-Looker` 除 `read` 外几乎全禁
- `Atlas` 禁止 `task` 和 `call_omo_agent`
- `Prometheus` 通过 hook 强制只允许修改 `.md`

这说明项目不是把 agent 当成“同一个模型套不同 prompt”，而是当成“具有不同能力边界的运行时角色”。

## 7. Team mode 兼容性

并不是所有 agent 都适合进 team mode。项目明确把 team mode 资格分成三档：[packages/omo-opencode/src/agents/AGENTS.md](/Users/liulei/aiS/oh-my-openagent/packages/omo-opencode/src/agents/AGENTS.md:48)

- `eligible`：`sisyphus`、`atlas`、`sisyphus-junior`
- `conditional`：`hephaestus`
- `hard-reject`：`oracle`、`librarian`、`explore`、`multimodal-looker`、`metis`、`momus`、`prometheus`

这个设计非常合理，因为 team mode 要求成员能独立推进工作，而只读顾问型 agent 不适合直接作为团队成员常驻。

## 8. 一条典型协作链

如果把它们串起来，可以想象一条常见路径：

1. `Sisyphus` 接到复杂任务。
2. 先让 `Explore` 看代码结构，或让 `Librarian` 查外部资料。
3. 若需要更系统的规划，切到 `Prometheus` 或借助 `Metis` 预分析。
4. 进入实施阶段后，交给 `Hephaestus` 或 `Sisyphus-Junior` 执行。
5. 对方案质量不放心时，再让 `Momus` 做评审。
6. 若任务本身是清单型推进，则由 `Atlas` 负责逐项闭环。

也就是说，这 11 个 agent 组成的不是树状主从关系，而是一个“按职责切面的协作网络”。

## 9. 为什么这套设计有意思

我觉得这套 agent 体系最有意思的地方有三点：

- 它把“规划、执行、审查、搜索、视觉分析”拆成不同运行时角色。
- 它用工具限制和 hook，而不是只靠 prompt 自觉，来保证角色边界。
- 它已经在为多 harness 复用做准备，所以 prompt、skills、core logic 被持续抽离到更通用的层里。

## 10. 一句话总结

`oh-my-openagent` 的 11 个内置 agent，本质上是一套分工严密的“多角色软件团队模拟器”：有人负责总控，有人负责施工，有人负责查资料，有人负责挑刺，有人只负责写计划。
