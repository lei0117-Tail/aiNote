# M09 上下文压缩 —— 当对话太长怎么办

> [!abstract] 核心结论
> Compaction 把旧消息变成结构化摘要替代原始消息,既腾空间又保留关键信息。核心时序:==压缩在两轮对话之间发生==,不在对话进行中。六个环节:触发判断 → 找切割点 → 分割 → 生成 6 section 结构化摘要 → 存 CompactionEntry → 下次运行 buildSessionContext 重建。

承接 [[M08-上下文工程-有限窗口装无限对话]]——`transformContext` 是扩展点,真正"动手压缩"的核心是 Compaction。

---

## 一、问题:对话越来越长,窗口装不下了

Agent 对话有状态——每轮发完整历史。50 轮 × 平均 3000 token = 150,000 token。Claude Sonnet 窗口 200,000。快满了。满了报错 `prompt is too long` 对话中断。

最直觉解法是删旧消息,但 Agent "失忆"——不记得最初任务、决策、改了哪些文件。Pi 的解法是==压缩:旧消息变结构化摘要,用摘要替代原始消息==。

```
压缩前(185,000 token):              压缩后(约 60,000 token):
┌── 第1-30轮(135K) ──┬── 第31-50轮(50K)──┐   ┌── 摘要(10K) ──┬── 第31-50轮(50K)──┐
│  原始消息(大量工具结果)│  原始消息(近期)    │   │ 结构化总结     │  原始消息(完整保留)│
└────────────────────┴──────────────────┘   └───────────────┴──────────────────┘
```

> [!important] 关键时序:压缩发生在两轮对话之间
> ==压缩不是对话进行中触发,而是在两轮之间发生==:
> ```
> 用户问 → Agent 回答 → agent_end 事件
>                              │ 检查 token:超阈值了吗?
>                   ┌──────────┴──────────┐
>                   ▼                     ▼
>                没超 → 等下一轮       超了 → 立刻压缩
>                                       ├─ 找切割点
>                                       ├─ 生成摘要
>                                       └─ CompactionEntry 写进 Session Tree
>                                              │ 下一轮用户问时:
>                                              ▼ buildSessionContext() 重建
>                                              → CompactionSummaryMessage 替代旧消息
>                                              → LLM 看到"摘要 + 近期消息"
> ```
> 这是理解整章的钥匙——所有细节都围绕"两轮之间"时序展开。

## 二、什么时候压缩:红灯亮起

### 触发条件

```js
function shouldCompact(contextTokens, contextWindow, settings): boolean {
    if (!settings.enabled) return false;
    return contextTokens > contextWindow - settings.reserveTokens;
}
```

代入:`contextWindow=200,000`,`reserveTokens=16,384`。当 `contextTokens > 183,616` 时触发。`reserveTokens` 是为 LLM 回复预留的空间。

### Token 估算:不精确但够用

```js
// compaction.ts:256-296
function estimateTokens(message: AgentMessage): number {
    let chars = 0;
    // 按 message.role 累加 text/thinking/toolCall/command/output/summary 字符数
    return Math.ceil(chars / 4);  // chars / 4
}
```

> [!warning] 已知精度问题:中文低估
> 英文 4 字符 ≈ 1 token(估算接近)。但中文 1 汉字实际约 1-2 token,`chars/4` 只算 0.25 token——==纯中文场景严重低估==,Pi 觉得"还没到阈值"实际已接近上限。
>
> 为什么用不精确估算?==宁可高估不可低估==。高估最多多压缩一次(无害);低估 API 报错(有害)。用精度换安全的保守策略。

### 两种触发场景

| 场景 | 何时触发 | 含义 |
|---|---|---|
| 预防性压缩 | token 超阈值(183,616)但没报错 | 提前压缩避免 API 报错 |
| 应急性压缩 | API 返回上下文溢出错误 | 补救措施,先压缩再重试 |

## 三、在哪切:切割点算法

### 不是哪里都能切

`ToolResult` 必须紧跟触发它的 `AssistantMessage`(含 ToolCall)。把 ToolCall 留保留区、ToolResult 切到压缩区,模型会看到"我调了 read 但结果在哪?"——上下文断裂。==切割点必须是有效切割点——不破坏消息对的位置==。

```
entry:  0    1    2     3      4    5     6      7     8
       hdr  usr  ass   tool   usr  ass   tool   ass   tool
                                     ↑
       有效切割点 = [1(usr), 2(ass), 4(usr), 5(ass), 7(ass)]
       注意:3(tool)、6(tool)、8(tool) 全部被排除
```

`findValidCutPoints` 规则:`user` 和 `assistant` 合法,`toolResult` 不是。注释:"When we cut at an assistant message with tool calls, its tool results follow it and will be kept."

> [!important] 切点语义:保留区的起点
> 切点不是"被切掉的最后一条",而是=="保留区的第一条"==。
> - 切点 = user:user 进保留区,后面的 assistant+toolResult 也跟着进→这个 Turn 完整保留
> - 切点 = assistant:会切断 Turn(user 在压缩区,assistant 在保留区)

==在 user 后切最安全==——天然保证 Turn 完整。

### 向后遍历:保护最重要的东西

`findCutPoint`(`compaction.ts:392-454`)从后往前累积:
```
从最新消息往回走,累积 token 数。
当累积量 >= keepRecentTokens(20,000)时停止。
在停止位置之后找最近的有效切割点——那里就是切刀。
```

> [!question] 为什么从后往前?
> ==最近的上下文最重要==。模型需知道"刚才做了什么""刚才读了什么文件""用户最新说了什么"。往回走直到累积够 20,000 token,确保保留足够近期上下文。

切割结果:切割点之前 → `messagesToSummarize`(被压缩);之后 → `kept`(保留)。

## 四、切掉的部分怎么处理:结构化摘要

### 摘要格式:不是自由文本,是填表

Pi 要求 LLM 填固定格式表格——==6 个 section==:

```
## Goal                    ← 用户最初要做什么
## Constraints & Preferences  ← 有什么约束
## Progress                ← 做了什么(Done / In Progress / Blocked)
## Key Decisions           ← 关键决策
## Next Steps              ← 下一步做什么
## Critical Context        ← 不能忘记的关键信息
```

> [!tip] 为什么用结构化格式?
> 自由文本容易遗漏——LLM 可能花大篇幅描述有趣技术细节,却忘了记录用户核心需求。==固定 section 强制 LLM 覆盖每个维度,减少遗漏==。Progress 的 Blocked 子项专门记录"卡住的事"——LLM 新一轮看到可优先解锁。

### 摘要生成:一次 LLM 调用

```
原始消息(AgentMessage[])
    │ 序列化
    ▼ "[User]: 帮我修 auth.ts\n[Assistant tool calls]: read(path=...)\n..."
    │ LLM 调用(摘要 prompt)
    ▼ 结构化摘要 ## Goal / ## Progress ...
```

### 增量更新:不是每次从零开始

```
第一次压缩: 输入第1-30轮 → 摘要 A
第二次压缩: 输入 摘要 A + 第31-50轮 → 摘要 B(在 A 基础上合并新信息)
```

LLM 做的是==更新而非重写==——已有 Goal/Constraints 保留,新增 Progress 追加。比每次从零写更稳定,避免"每次压缩摘要漂移一点"的累积误差。用 `UPDATE_SUMMARIZATION_PROMPT`。

### 文件跟踪:压缩不只是摘要文字

```xml
<read-files>
src/auth.ts
src/utils/hash.ts
</read-files>

<modified-files>
src/auth.ts
</modified-files>
```

==跨压缩累积==——第二次压缩时 `previousSummary` 的文件列表合并进新摘要。即使经多轮压缩,Agent 仍知道整个会话读过哪些文件、改过哪些文件。

## 五、极端情况:Turn 分割

user 切点天然保证 Turn 完整;assistant 切点会切断 Turn。

> [!question] 为什么允许 assistant 切点?
> 答案藏在 token 控制精度:
> ```
> entry:  1    2     3     4     5    6     7    8
>        usr  ass  tool  ass  tool  ass  tool  ass
>                                   ↑ 向后累积到这里预算用完
> ```
> - 只允许 user 切点:最近 user 是 entry 1→保留区从 1 开始要保留 8 个 entry,但预算只够 2-3 个→==压缩失败==
> - 允许 assistant 切点:选 entry 6→保留区只有 6-8 共 3 个,精确控制 token
>
> ==权衡:优先保证压缩能生效,然后用 turnPrefix 机制弥补 Turn 完整性损失==。

### turnPrefix 机制:被切断的 Turn 怎么办?

```
entry:  1    2     3     4     5     6      7     8    9
       usr  ass  tool  ass  tool  tool   ass   tool  ass
         ↑    └────── turnPrefixMessages ──────┘  └kept┘
       turnStart=1          (entries 2-6)        entries 7-9
       切点 entry 7(assistant),但 entry 1(user)是它 Turn 起点
       → entry 1 在主摘要里压缩
       → entry 2-6 是"被切断的 Turn 前缀",单独生成 turnPrefix 摘要
```

`turnPrefixMessages`(`compaction.ts:698-705`)用专门的 `TURN_PREFIX_SUMMARIZATION_PROMPT` 单独生成前缀摘要,和主摘要==并行生成==(`Promise.all`,L784-813),最后合并。

| 摘要类型 | 覆盖 | 格式 |
|---|---|---|
| 主摘要 | 被压缩的完整历史(多个完整 Turn) | 6 section 结构化 |
| turnPrefix 摘要 | 被切断的半个 Turn(user 在主摘要、assistant 在保留区) | ==更轻量 3 段==(Original Request / Early Progress / Context for Suffix) |

两份合并存同一 CompactionEntry,下一轮一起注入。

## 六、压缩结果如何生效

### CompactionEntry:压缩结果的物理形态

```ts
{
    type: "compaction",
    summary: "## Goal\nFix auth.ts...\n## Progress\n...",
    tokensBefore: 185000,              // 压缩前 token(诊断和审计)
    firstKeptEntryId: "e30",           // 保留的起始 entry id
    details: {                         // 文件操作跟踪(extractFileOperations)
        readFiles: ["src/auth.ts", "src/utils/hash.ts"],
        modifiedFiles: ["src/auth.ts"],
    },
    // ... id/parentId/timestamp 等 SessionEntryBase 字段
}
```

### 上下文重建

下次运行 `buildSessionContext()` 根据 CompactionEntry 重建:
```
重建后上下文:
├── CompactionSummaryMessage(role:"compactionSummary")
│     content = 摘要文本(第6章:convertToLlm 翻译成 <summary> 标签 UserMessage)
├── 保留的原始消息(entry 30 之后)
└── (新消息运行中追加)
```

LLM 看到的是:"The conversation history before this point was compacted into the following summary: …" ==之前几十轮对话变成摘要,但知道目标/进度/决策/文件操作记录==。

### 自动压缩集成

嵌入 AgentSession 的 `agent_end` 事件处理:
```
Agent 运行结束(agent_end 事件)
    │ 检查 shouldCompact()?
    ├── 不需要 → 结束
    └── 需要 → findCutPoint → 序列化+LLM 调用生成摘要
              → 追加 CompactionEntry 到 Session Tree
              → 下次运行 buildSessionContext 使用压缩后上下文
```

### 两套事件

- `compaction_start`(reason: "manual" | "threshold" | "overflow")
- `compaction_end`(携带压缩结果或错误信息)

UI 订阅显示"正在压缩上下文…"进度。

## 七、完整链路回顾

```
① 触发判断
   shouldCompact() → contextTokens(185K) > contextWindow(200K) - reserve(16K)
② 找切割点
   向后遍历 → 累积 token 到 keepRecent(20K) → 找最近有效切割点(排除 toolResult)
③ 分割消息
   切割点之前 → messagesToSummarize(被压缩);之后 → kept(保留)
④ 生成摘要
   序列化消息 → 调 LLM 填 6 section → 传 previousSummary 增量更新 → 合并文件跟踪列表
⑤ 存储结果
   CompactionEntry 追加到 Session Tree
⑥ 下次运行时
   buildSessionContext() → CompactionSummaryMessage 替换旧消息 → convertToLlm 翻译成 UserMessage
```

## 八、设计精华:三个值得带走的思路

### 1. 向后遍历 + 合法切点:保护最重要的东西

`findCutPoint` 不是"找哪里能切",而是=="找哪里值得保留"==——从最新往回走直到累积够 `keepRecentTokens`(默认 20K)。判断:==最近上下文最重要==。切点排除 `toolResult` 是协议硬约束(toolResult 必须紧跟 toolCall),不可妥协。

### 2. 结构化摘要:用固定模板对抗 LLM 的"自由发挥"

`SUMMARIZATION_PROMPT` 强制填 6 个 section。==自由文本摘要失败模式:LLM 被"有趣内容"吸引,花大篇幅描述技术细节,忘了记录用户核心需求==。固定 section 强制每维度至少扫一遍,把"易遗漏"变"必须填"。加上增量更新避免累积误差。==用 prompt 设计对抗 LLM 认知偏差的范例==。

### 3. 文件跟踪累积:编码 Agent 的领域特定知识

`extractFileOperations` 从两来源累积:上一次压缩的 `details.readFiles`/`modifiedFiles`;这次被压缩消息里所有工具调用涉及的文件(read→readFiles,edit/write→modifiedFiles)。

> [!info] 为什么单独跟踪文件?
> 对编码 Agent,"改过哪些文件"是至关重要的元信息——比"对话讨论过什么"更精确、更可验证。LLM 看列表知道哪些文件被触碰过,避免重复读、避免覆盖他人改动。==领域知识嵌入通用机制==——压缩算法本身通用,但通过 `details` 字段承载领域特定信息。
