# M04 模型调用 —— 一行代码驾驭多个模型

> [!abstract] 核心结论
> 一行 `streamSimple(model, context)` 背后是 ==三层架构==:统一入口(查表派活)→ 事件协议(12 种统一事件)→ 翻译器(每个精通一种 Provider 方言)。Agent Loop 自始至终只看到统一事件流,不知道中间发生了多少翻译。

承接 [[M03-Agent-Loop-让模型转动的引擎]]——Loop 调模型那行代码背后发生了什么。

---

## 一、问题:同一段对话,不同模型要"翻译"成不同格式

用户说"帮我读一下 main.ts",Pi 内部统一格式:
```
{ role: "user", content: "帮我读一下 main.ts", timestamp: 1748697600000 }
```

发给不同模型要翻译成各家格式:

| Provider | 格式 |
|---|---|
| Anthropic | `{ role:"user", content:[{ type:"text", text:"..." }] }`(数组+type) |
| OpenAI | `{ role:"user", content:"..." }`(但工具结果要单独 `{ role:"tool" }`) |
| Google | `{ role:"user", parts:[{ text:"..." }] }`(parts 替代 content) |
| Bedrock | `{ role:"user", content:[{ text:"..." }] }`(text 无 type 字段) |

### 四个维度全都不一样

| 维度 | 差在哪 | 例子 |
|---|---|---|
| 消息格式 | 字段名和结构不同 | Anthropic `content[]` vs Google `parts[]` |
| 流式传输 | 逐字返回机制不同 | Anthropic 发原始 SSE 要自己解析,OpenAI SDK 直接返回结构化 chunk |
| 思考模式 | 深度思考参数完全不同 | Anthropic `thinking.budget_tokens` vs OpenAI `reasoning_effort` |
| 缓存控制 | 标记不变内容方式不同 | Anthropic `cache_control` 标记 vs Bedrock `cachePoint` 节点 |

四个维度 × 30+ Provider,组合差异量巨大。

---

## 二、解法:三层架构,各管一件事

```
第一层 · 统一入口    →  "接收请求,查出该找谁处理"
第二层 · 事件协议    →  "约定输出格式——不管谁处理,交回来的都是这个样子"
第三层 · 翻译器      →  "真正干活——每个翻译器精通一种 Provider 方言"
```

> [!quote] 国际翻译公司类比
> - 第一层(前台):客户进门,查通讯录找翻译员派活
> - 第二层(标准报告模板):不管翻译员翻什么语言,交出来的报告必须用公司统一格式
> - 第三层(翻译员们):每个精通一种语言,内部怎么翻译是自己的事,输出必须符合第二层格式
>
> Agent Loop 是"客户"——交给前台,拿标准报告,从不直接接触翻译员。

### 第一层:统一入口 stream()

```js
// compat.ts
export function stream(model, context, options?) {
  const provider = resolveApiProvider(model.api);  // 查表:这个 model 该找谁?
  return provider.stream(model, context, options);  // 派给翻译器
}
```

就两步:==查表,派活==。`model.api` 是字符串(如 `"anthropic-messages"`),启动时所有翻译器注册进"通讯录":

```js
const BUILTIN_APIS = [
  ["anthropic-messages",       anthropicMessagesApi()],
  ["openai-completions",       openAICompletionsApi()],
  ["google-generative-ai",     googleGenerativeAIApi()],
  ["bedrock-converse-stream",  bedrockConverseStreamApi()],
  // ... 还有 5 个
];
```

### 第二层:事件协议(12 种 AssistantMessageEvent)

```
start                                     ← 流开始了
├── text_start → text_delta → ... → text_end        ← 文字
├── thinking_start → thinking_delta → ... → thinking_end  ← 思考
├── toolcall_start → toolcall_delta → ... → toolcall_end  ← 工具调用
done   (reason: stop / length / toolUse)             ← 正常结束
error  (reason: error / aborted)                     ← 出错
```

模式:模型回复分三类(文字/思考/工具调用),每类"开始→逐字增量→结束"三步,再加流开始和流结束信号。

> [!important] 每个事件都携带 partial: AssistantMessage
> 当前消息的完整快照。第 3 章的"原地替换"就是这个——用 `partial` 覆盖 context 最后一条消息,不用自己拼接增量。

### 第三层:翻译器(5 步工作流程)

```
翻译器(model, context, options)
├── 1. 创建客户端      API Key 初始化(翻译员确认带了字典)
├── 2. 构建请求参数    统一格式 → Provider 私有格式(如 content→parts)
├── 3. 发送请求        SDK 或直接 HTTP
├── 4. 处理响应流      Provider 私有事件 → 12 种统一事件
└── 5. 发送终止事件    成功→done;失败→error
```

第 2 步(请求翻译)和第 4 步(响应翻译)是核心工作量,每个翻译器上千行代码的主要原因。

Anthropic 第 4 步翻译规则示例:
```
content_block_start (type:"text")      →  text_start
content_block_delta (text_delta)       →  text_delta
content_block_start (type:"tool_use")  →  toolcall_start
message_delta (stop_reason)            →  done(映射终止原因)
```

终止原因映射:Anthropic `"end_turn"` → Pi `"stop"`,`"tool_use"` → `"toolUse"`。每个 Provider 命名不同,Pi 统一成自己的术语。

### StreamFunction:翻译器的"入职要求"(宪法)

```ts
export type StreamFunction<TApi extends Api, TOptions> = (
  model: Model<TApi>,
  context: Context,
  options?: TOptions,
) => AssistantMessageEventStream;  // ← 必须返回统一事件流
```

三条规则:
1. **输入相同**:所有翻译器接受同样三个参数
2. **输出相同**:必须返回 `AssistantMessageEventStream`
3. ==错误不抛异常==:API 失败时不 `throw`,发 `{ type:"error" }` 事件

第 3 条呼应第 3 章的"永不抛出"——`stopReason:"error"`/`"aborted"` 是翻译器 catch 块在异常时注入的。

## 三、怎么用:从调用到接入新模型

### stream() vs streamSimple()

| 函数 | 作用 |
|---|---|
| `stream()` | 底层入口,只做"查表+派活",不管思考级别翻译 |
| `streamSimple()` | 在 stream 上包一层便捷功能——自动处理 ThinkingLevel 翻译、调整 maxTokens。实际开发常用 |

```js
const stream = streamSimple(model, context, { reasoning: "high" });
for await (const event of stream) {
  switch (event.type) {
    case "text_delta":   // 文字增量
    case "toolcall_end": // 完整工具调用
    case "done":         // 本轮结束,看 stopReason
    case "error":        // errorReason 是 "error" 或 "aborted"
  }
}
```

不管 model 是 Claude、GPT 还是 Gemini,`streamSimple` 返回同一种事件流。

### 接入新模型三步

**第 1 步**:写翻译器(对应第三层)——符合 `StreamFunction` 签名的函数:请求方向翻译消息格式、响应方向翻译成 12 种统一事件、异常 push error 事件不 throw。工作量最大但是==一次性工作==。

**第 2 步**:注册翻译器(对应第一层)——往"通讯录"加记录:
```js
registerApiProvider({
  api: "your-model-api",
  stream: yourStreamFunction,
  streamSimple: yourSimpleFunction,
});
```

**第 3 步**:配置模型信息——`api` 字段指向第 2 步注册的名字:
```js
const yourModel: Model = {
  id: "your-model-id", api: "your-model-api",
  provider: "your-provider", baseUrl: "https://api.your-model.com",
};
```

> [!success] Agent Loop 一行都不用改
> 事件系统、会话管理、压缩算法全部自动适配。==新模型接入成本被限制在"写一个翻译器"这一个点==。

## 四、【进阶】翻译器内部:SSE 解析与思考模式方言

### 流式传输:Anthropic 和 OpenAI 解析方式完全不同

```
Anthropic(翻译器自己做脏活):
  原始 HTTP → 逐行读取 → 分离 event/data → JSON 解析(含容错) → 内部事件
OpenAI(SDK 帮你做脏活):
  client.chat.completions.create() → AsyncIterable<Chunk> → 结构化数据
```

> [!tip] 为什么不用统一 SDK?
> 不是所有 Provider 都有成熟 SDK。Pi 策略:有 SDK 就用(OpenAI/Google),没 SDK 就自己解析(Anthropic)。不管内部怎么实现,最终都翻译成统一 12 种事件。

### 思考模式:四种"思考",四种参数

```
Anthropic: params.thinking = { type:"enabled", budget_tokens:16384 }   // token 预算
OpenAI:    params.reasoning_effort = "high"                             // 努力程度
Google:    config.thinkingConfig = { includeThoughts:true, thinkingLevel:"high" }
```

Anthropic 自己都有两种模式:新版"自适应思考"(模型自决)、旧版"预算思考"(固定上限)。

### Pi 的统一:ThinkingLevel 五级刻度

```
off    minimal    low    medium    high    xhigh
 │        │       │       │        │       │
不思考  1024tk  2048tk  8192tk  16384tk  模型最大值
```

上层只说 `reasoning:"high"`,翻译器查表翻译。每个 `Model` 对象自带 `thinkingLevelMap`(翻译表)。请求级别不支持时 `clampThinkingLevel()` 回退——==先向上找==(思考更多通常比更少安全),找不到再向下。`streamSimple()` 自动完成这套翻译。

## 五、【进阶】缓存控制与错误处理

### 缓存控制:让模型"算更少"

对话有状态——每轮都发完整历史。聊 50 轮就重算前 49 轮。缓存告诉服务器"这些没变,别重算"。命中 token 按缓存读取价计费(通常正常输入价 1/10),200K 对话历史能省约 90% 输入成本。

Pi 抽象成三个语义级别:`type CacheRetention = "none" | "short" | "long"`

| Provider | `none` | `short` | `long` | 打点位置 |
|---|---|---|---|---|
| Anthropic | 不打标记 | `cache_control:{type:"ephemeral"}`(5min TTL) | 加 `ttl:"1h"`(仅新模型) | system 末尾+最后 tool+最后 user(rolling) |
| Bedrock | 不插节点 | 插独立对象 `{cachePoint:{type:DEFAULT}}` | 加 `ttl:ONE_HOUR` | system 块后+最后消息后 |
| OpenAI Responses | 不发 cache key | `prompt_cache_key:sessionId` | `prompt_cache_retention:"24h"` | 不打点——按 session key 自动匹配 |
| OpenAI 兼容(DeepSeek/Qwen) | 不打标记 | 按 Anthropic 风格 `cache_control` | 加 `ttl:"1h"` | 复用 Anthropic 三处策略 |

> [!info] 四家四种协议设计思路
> - **Anthropic** 像"贴便签":内容块附加 `cache_control` 字段
> - **Bedrock** 像"插路标":消息流特定位置插独立 cachePoint 对象
> - **OpenAI 原生** 像"按会员卡号查记录":不打标记,带 `prompt_cache_key`(sessionId),后端识别前缀重合度
> - **OpenAI 兼容** 最朴素:抄 Anthropic 便签协议(`cacheControlFormat:"anthropic"`)

> [!question] 为什么 Anthropic 选三个特定位置打点?
> 不是随便选——`system+tools` 是 Trace 内最稳定前缀,`最后一条 user message` 是 rolling 的"截止线"。Anthropic 规定每请求最多 4 个 cache breakpoint,这三个位置覆盖"完全不变+最近滚动"两段,是收益最大化又不超限额的最优解。

### 错误处理:编码到流里,不打断循环

```js
try {
  stream.push({ type: "done", reason: output.stopReason, message: output });
} catch (error) {
  output.stopReason = options?.signal?.aborted ? "aborted" : "error";
  output.errorMessage = error.message;
  stream.push({ type: "error", reason: output.stopReason, error: output });
}
```

异常被包装成事件,Agent Loop 收到后可重试、降级、报告给用户,循环不停。

> [!warning] 隐蔽问题:上下文溢出
> 有时请求没报错但模型返回空输出——输入 token 太多被服务端静默截断。Pi 的 `isContextOverflow()` 做==三重检测==(错误消息模式匹配、token 数对比、输出为零+length 停止),统一捕获不同 Provider 的溢出表现。

## 六、回到那一行代码

```
Agent Loop: streamSimple(model, context, { reasoning:"high" })
    │  ① streamSimple 处理思考级别翻译(查表→clamp→调整maxTokens)
    │  ② 调用 stream() → 前台查表 → 找到翻译器
    │  ③ 翻译器工作:统一格式→Provider 私有格式→发给模型→私有响应→12种统一事件
    │  ④ 返回 AssistantMessageEventStream
    └── Agent Loop: for await (event of stream) { ... }  ← 消费统一事件
```

Agent Loop 看到的只有 ④——一个干净的事件流。==复杂度被封装在翻译器里,外部接口保持简洁==。

---

## 设计精华:三条核心思路

1. **"协议 > 实现"设计法**。Pi 没设计 `BaseProvider` 抽象类让翻译器继承,而是定义事件协议(12 种)+ 函数签名(`StreamFunction`)。==不用继承因为翻译器间几乎无共同点==——Anthropic 和 Google 连字段名都不一样。协议只约定"输入什么、输出什么",不管中间怎么处理
2. **"统一枚举 + 映射表"策略**。ThinkingLevel 五级枚举,`ThinkingLevelMap` 让每个 Model 自带翻译表。比"取所有 Provider 交集"灵活(交集可能只剩 `"off"`),比"暴露各 Provider 原生参数"简洁(上层不需知 20 种参数名)
3. **"语义统一,实现分散"**。`cacheRetention`(none/short/long)是语义接口——上层说"我要长期缓存",不管底层打标记还是插节点。==语义接口描述"做什么",机制接口描述"怎么做"==
