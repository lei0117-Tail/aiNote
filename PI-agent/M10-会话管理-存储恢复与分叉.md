# M10 会话管理 —— 对话的存储、恢复与分叉

> [!abstract] 核心结论
> 会话存储要拆成 ==两个独立维度==:存哪里(coding-agent 选本地 JSONL 文件,接口允许换数据库)+ 长什么样(树 Session Tree,不是线性数组)。Session Tree 是 ==append-only 的树==——回退/分支不删数据,只是移动 `leafId` 指针。"认父不认子"是 append-only 的必要条件。

承接 [[M09-上下文压缩-对话太长怎么办]]——CompactionEntry 存 Session Tree,buildSessionContext 从树构建上下文。

---

## 一、问题:会话数据怎么存?

两个独立子问题(正交,可独立选择):
- **子问题 A**:存在哪里?(存储介质)
- **子问题 B**:长什么样?(数据结构)

### 子问题 A:存在哪里(介质)

Pi 的 coding-agent 选==本地 JSONL 文件==——每个会话一个 `.jsonl`,存用户本地磁盘项目目录下,一行一个 entry 纯文本。

> [!question] 为什么选文件不选数据库?
> - **单用户本地运行**:CLI 工具跑用户自己机器,无多用户并发/跨机器查询需求,数据库那套并发/索引/事务全过度设计
> - **会话跟项目走**:`cd /project-a` 打开 a 的历史,`cd /project-b` 打开 b 的——每个项目 `.pi/sessions/` 是对话档案
> - **零依赖零运维**:不需装 mysql、不起服务,开箱即用
> - **可读可调试**:JSONL 纯文本,可 `cat`/`grep`/编辑器打开

> [!info] 接口允许换数据库
> agent-core 层提供 `SessionStorage` 接口(`harness/types.ts:440`),自带 `JsonlSessionStorage`(文件)和 `InMemorySessionStorage`(内存,测试用)两个实现。但注意:==coding-agent 的 SessionManager 并未实现 agent-core 的 SessionStorage 接口==——两者独立两套实现,coding-agent 直接读写自己的 JSONL,没走 agent-core 抽象层。"接口存在但不强制复用"是 Pi 内部各包松耦合的真实案例。

### 子问题 B:长什么样(结构)

最直觉是线性数组 `messages=[msg1,msg2,...]`。但真实场景对话不总是线性:重试(退回上一轮重新生成)、分支(某节点尝试两种方案比较)、回退(走错路回岔路口)。

线性数组做不到"分叉不丢数据"。Pi 答案是 ==Session Tree——只追加、不修改、不删除的树==。回退/分支不是"删数据",而是"移动指针"。

| 维度 | 一般选择 | Pi 的选择 |
|---|---|---|
| 存哪里 | mysql 等数据库 | 本地 JSONL 文件(接口允许换) |
| 长什么样 | 线性数组 | 树(Session Tree) |

## 二、跟着真实会话看树怎么长出来

调试认证 bug 的 8 步操作:

```
步骤1: 切换到 Claude 4.6    步骤5: Agent 回复"问题在23行"
步骤2: 问"salt验证为什么失败" 步骤6: 回退到步骤2重来
步骤3: Agent 调 read 读 auth.ts  步骤7: 换思路问"先看hash函数实现"
步骤4: read 返回 auth.ts 内容    步骤8: Agent 调 grep+read 给新分析
```

### 第 1-5 步:主分支直线长出

每步只做两件事:创建新节点(带 parentId)+ 移动 leafId。没有任何旧节点被修改。

```
e1 (model_change)
 └── e2 (user: "salt 验证为什么失败?")
      └── e3 (assistant: read auth.ts)   ← 一条 AssistantMessage 同时含文本和 ToolCall
           └── e4 (toolResult: auth.ts 内容)  ← toolCallId 关联到 e3 的 ToolCall
                └── e5 (assistant: "问题在 23 行")  ← leafId
```

> [!note] 一条 AssistantMessage 同时含文本和工具调用
> 它们放同一个 content 数组,是同一个节点。不是"文本一个节点+工具调用一个节点"。

### 第 6 步:回退——关键转折

不满意分析想换思路,执行回退——==但没有删除任何节点==:

```js
branch(branchFromId: "e2"): void {
    this.leafId = "e2";   // 只改这一行
}
```

```
e1 (model_change)
 └── e2 (user: "salt 验证为什么失败?")
      ├── e3 (assistant: read auth.ts)   ← 旧分支还在,数据完整保留
      │    └── e4 (toolResult)
      │         └── e5 (assistant: "问题在 23 行")
      │
      ↑ leafId 现在指回 e2
```

e3、e4、e5 一个没删,只是不在"当前路径"上。==append-only 核心:回退不是删数据,是移动指针==。

> [!question] 为什么要保留?
> 你不知道以后会不会想回旧分支。新思路走半天没结果想退回去看原来分析——回退时删了就再也找不回来。

### 第 7 步:换思路重新问——新分支自然长出

```ts
e6: MessageEntry
    parentId: e2   ← 跟 e3 共享同一个父!这就是分支的本质
    message: { role: "user", content: "先看 hash 函数的实现" }
```

```
e2 (user)
 ├── e3 (assistant: read auth.ts) → e4 → e5
 └── e6 (user: "先看 hash 函数")   ← 新分支起点,leafId
```

### 第 8 步:新分支继续长

```
e1
 └── e2
      ├── e3 → e4 → e5
      └── e6 (user: "先看 hash 函数")
           └── e7 (assistant: grep hash)
                └── e8 (toolResult: grep 结果)
                     └── e9 (assistant: 新分析)   ← leafId
```

9 个节点分两个分支,所有数据完整保留。==对话是一棵树,每条消息是一个节点,回退/分支不删数据,只是移动指针==。

## 三、树上节点的解剖

### 一个完整 MessageEntry

```json
{
  "type": "message",
  "id": "e3",
  "parentId": "e2",
  "timestamp": "2026-07-03T10:23:45.000Z",
  "message": {
    "role": "assistant",
    "content": [
      { "type": "text", "text": "让我读一下 auth.ts" },
      { "type": "toolCall", "id": "call_001", "name": "read",
        "arguments": { "path": "src/auth.ts" } }
    ],
    "model": "claude-sonnet-4-6",
    "stopReason": "toolUse",
    "usage": { "input": 1250, "output": 80 }
  }
}
```

| 字段 | 干什么 | 设计动机 |
|---|---|---|
| `type: "message"` | 区分节点类型 | 树上不止消息,还有 model_change/compaction 等 |
| `id: "e3"` | 节点唯一标识 | 别的节点通过 parentId 指向它 |
| `parentId: "e2"` | 指向父节点 | ==认父不认子==——节点不知道自己有哪些子节点 |
| `timestamp` | 创建时间 | 排序、调试用 |
| `message` | 真正的消息载荷 | role+content+model 等(第6章) |

> [!important] "认父不认子"是 append-only 的必要条件
> `parentId` 是单向的——节点知道自己从哪来,但父节点不知道自己有哪些孩子。==这不是疏忽是设计==——若父节点维护 children 列表,追加新子节点时就得修改父节点,违反 append-only。
>
> 反证:第 7 步从 e2 长出新分支 e6,若"认子",e2 的 children 从 `[e3]` 改成 `[e3,e6]`——需修改 e2,但 append-only 规定节点不可变,矛盾。==只有"认父不认子"才能让追加操作不修改任何旧节点==。配合 `byId` 映射表可反向查询所有子节点。

### 9 种 Entry 类型,按职责分三组

**第一组:进 LLM 上下文(4 种)**——变成 messages 数组一项发给 LLM:

| 类型 | 产生什么消息 | 例子 |
|---|---|---|
| `MessageEntry` | User/Assistant/ToolResultMessage | 第2-5步所有对话消息 |
| `CustomMessageEntry` | CustomMessage(第6章自定义消息) | 扩展注入的特殊消息 |
| `CompactionEntry` | CompactionSummaryMessage(替换旧消息) | 第9章压缩结果 |
| `BranchSummaryEntry` | BranchSummaryMessage(被抛弃分支摘要) | §四分支摘要 |

**第二组:影响后续 LLM 调用(2 种)**——不产生消息,改后续调用参数:

| 类型 | 改变什么 | 例子 |
|---|---|---|
| `ModelChangeEntry` | 后续用哪个模型 | 第1步切到 Claude 4.6 |
| `ThinkingLevelChangeEntry` | 后续思考级别 | 用户调整思考强度 |

**第三组:纯元数据,不影响 LLM(3 种)**——给 UI 或扩展用:

| 类型 | 干什么 |
|---|---|
| `LabelEntry` | 给节点贴书签("这里是关键点") |
| `SessionInfoEntry` | 会话元信息(名称、创建者) |
| `CustomEntry` | 扩展自己存的元数据 |

> [!question] 为什么类型分这么细?
> `buildSessionContext()` 需按类型分派处理——是消息就进 messages 数组,是状态变更就改状态变量,是元数据就跳过。==如果只有一种类型,处理逻辑塞满 if-else,可读性和扩展性都差==。

## 四、三个核心操作 + 分支摘要

### 操作 1:追加——O(1) 不改任何旧节点

```js
1. 创建新 Entry(含 id、parentId 指向当前 leafId、payload)
2. 存入 byId 映射表(id → entry)
3. leafId = 新 entry 的 id
```

没有修改任何旧节点——只是创建新节点时让 parentId 指向当前 leafId。

### 操作 2:回退——只移动 leafId

```js
branch(branchFromId: "e2"): void {
    if (!this.byId.has(branchFromId)) throw new Error(`Entry ${branchFromId} not found`);
    this.leafId = "e2";   // 核心就是这一行
}
```

核心 `leafId = branchFromId`(外加存在性检查)。没有删除 e3/e4/e5——它们还在 byId 里、还在 .jsonl 文件里。==回退只是说"以后追加新节点时 parentId 指向 e2"==。

### 操作 3:分支——回退后追加的自然结果

回退到 e2 后再追加 e6,e6 的 parentId 自动就是 e2。==分支不是独立操作,是"回退+追加"的组合效果==。

### 分支摘要:BranchSummaryEntry(回退时的可选项)

从 e5 回退到 e2,旧分支(e3-e5)成"被抛弃分支"。数据完整保留但当前路径 LLM 看不到。若希望当前路径 Agent 大致知道之前试过什么,用 `branchWithSummary()`:

```ts
branchWithSummary(fromId: "e5"): Promise<void> {
    // 1. 把 e3-e5 喂 LLM 生成结构化摘要
    // 2. 创建 BranchSummaryEntry,parentId 指向 e2(与 e3-e5 同父)
    // 3. 摘要格式同压缩摘要(Goal/Progress/Decisions)
}
```

```
e2 (user)
 ├── e3 (assistant: read auth.ts) → e4 → e5
 ├── e_BranchSummary ("之前试过 read auth.ts,发现 salt 编码问题但未解决根因")
 └── e6 (user: "先看 hash 函数")
```

> [!info] BranchSummaryEntry vs CompactionSummaryMessage
> BranchSummaryEntry 是被抛弃分支的"遗言",不是真实对话。buildSessionContext 转换成 `BranchSummaryMessage`(区别于压缩的 `CompactionSummaryMessage`——见 `session-manager.ts:397` createBranchSummaryMessage vs `:403` createCompactionSummaryMessage;第6章:convertToLlm 翻译成 `<summary>` 标签 UserMessage)。

==可选==——觉得旧分支不重要直接 `branch()` 就够。`branchWithSummary()` 给"想保留历史精华但不想保留完整对话"的场景。

## 五、从树到 LLM 上下文:buildSessionContext

LLM 不认识树,只接受线性 messages 数组(第6章:user/assistant/toolResult)。每次调 LLM 前要把树"压扁"——这就是 `buildSessionContext()`。

### 第一步:路径遍历——从 leaf 往回走到 root

```js
const path: SessionEntry[] = [];
let current = byId.get(leafId);   // e9
while (current) {
    path.push(current);   // 先按 leaf → root 顺序
    current = current.parentId ? byId.get(current.parentId) : undefined;
}
path.reverse();           // 反转为 root → leaf
// path = [e1, e2, e6, e7, e8, e9]
```

==e3、e4、e5 不在 path 里——不在当前分支上==。当前路径只看 leaf 到 root 这条线,其他分支数据不发给 LLM。

### 第二步:按类型分派处理

```
e1 (model_change)   → 更新状态变量 model = "claude-sonnet-4-6",不进 messages
e2 (user message)   → 推入 messages
e6 (user message)   → 推入 messages
e7 (assistant+ToolCall) → 推入 messages
e8 (toolResult)     → 推入 messages
e9 (assistant)      → 推入 messages
```

> [!note] 连续两条 user 消息
> e2 和 e6 都是 user。大多 Provider 允许,有些要求合并——Pi 在 convertToLlm 那层处理(第6章翻译规则)。

### 状态变量:覆盖式提取

model_change 和 thinkingLevel_change 不进 messages,但影响"用什么参数调 LLM"。==沿路径从 root 走到 leaf,遇到变更就覆盖==:

```
e1 (model_change:"claude-sonnet-4-6") → model = "claude-sonnet-4-6"
e2-e9(无 model_change)                → model 保持不变
```

多条 model_change 最后一次覆盖生效(最后生效语义)。

> [!important] 初始值兜底
> `buildSessionContext` 中 `model` 状态变量初始值是 `null`(`session-manager.ts:367`)。路径无 model_change 节点时返回 `model:null`,由调用方兜底用 session 启动时配置的初始 model。==assistant 消息不携带"用哪个模型生成"信息——model 完全由 model_change 节点决定==。

> [!success] 为什么把"切换模型"存成节点而不是状态变量?
> 节点能完整记录"什么时候切、在哪个位置切",状态变量只能存最后值。==回退到切换模型之前的节点,buildSessionContext 走的路径不含那条 model_change,model 自动回到切换前值==。节点化状态让回退天然正确。

### CompactionEntry 特殊处理:选择性收集

```
e1 (user)         ← 早期对话(已被压缩)
e2 (assistant)    ← 被压缩
e3 (assistant)    ← 被压缩
e4 (compaction)   ← 压缩节点,firstKeptEntryId = "e3"
e5 (user)         ← 压缩后保留的近期消息
e6 (assistant)
```

遍历到 e4 时按 `firstKeptEntryId` 选择性收集:
- 生成一条 `CompactionSummaryMessage`(来自 e4 summary)推入 messages 开头
- e4 之前的 entry 只收集 `firstKeptEntryId`(e3)及之后——e1、e2 丢弃,e3 保留
- e4 之后所有 entry 正常收集

> [!tip] 压缩不是破坏性的
> ==不是真删 e1、e2==(append-only 不允许删),而是 buildSessionContext 遍历时按 firstKeptEntryId "跳过"它们。回退到 e4 之前的位置,路径不含 e4,e1-e3 又作为正常消息出现——==压缩只是"当前路径上"的视图==。

## 六、JSONL 持久化细节

### 格式:一行一个 Entry

```jsonl
{"type":"session","version":3,"id":"UUIDv7","cwd":"/project","timestamp":"..."}
{"type":"model_change","id":"e1","parentId":null,"provider":"anthropic","modelId":"claude-sonnet-4-6","timestamp":"..."}
{"type":"message","id":"e2","parentId":"e1","message":{"role":"user","content":[{"type":"text","text":"salt验证为什么失败?"}]},"timestamp":"..."}
{"type":"message","id":"e3","parentId":"e2","message":{"role":"assistant",...},"timestamp":"..."}
...
{"type":"message","id":"e6","parentId":"e2","message":{"role":"user",...},"timestamp":"..."}
```

第一行 Session Header(`type:"session"`),后续每行一个 Entry。

> [!info] 值得注意的细节
> - e6 的 parentId 是 e2——用 `grep '"parentId":"e2"'` 就能找到所有从 e2 长出的子节点(看出分支)
> - timestamp 是 ISO 字符串(人类可读)
> - id 是 8 位短 UUID(如 `a1b2c3d4`),比完整 UUID 省空间,会话内冲突概率足够低

> [!question] 为什么用 JSONL 不用单个 JSON?
> ==JSONL 是行级追加的==——新 Entry 直接 `appendFileSync` 到文件末尾,不需读入-修改-重写整个文件。和 append-only 树设计完美契合:树只追加不修改,文件也只追加不重写。

### 延迟写入:避免"有问无答"的半截对话

首次 assistant 消息到达前,写入延迟。四种情况:

| 已有 assistant? | 已 flushed? | 行为 |
|---|---|---|
| 没有 | 已 flushed | 立即 append 当前 entry |
| 没有 | 未 flushed | 标记"未 flushed",不写盘——等 assistant 到来 |
| 有 | 未 flushed | 重写整个文件(header + 所有积压 entry),`openSync("wx")+writeFileSync` 保证原子性,标记已 flushed |
| 有 | 已 flushed | 立即 append 当前 entry |

> [!warning] 为什么要这套复杂逻辑?
> 避免"有问无答"的半截对话残留——用户问了但 Agent 没回(网络断、API 报错),如果立即每条用户消息写盘,下次打开会看到孤零零的用户消息悬在那儿没对应回复。==延迟到首次 assistant 消息到达再批量写入,保证落盘对话至少有一对完整 user-assistant 往返==。

### 偶尔的全文件重写

两种情况触发 `writeFileSync`:
- **创建分支副本**:克隆会话到新 .jsonl,复制当前路径所有 entry
- **修复损坏会话文件**:发现格式异常重新规范写一遍

==重写不破坏 append-only 原则==——重写产生新文件或新格式,原历史数据完整保留在重写后内容里。

## 七、两层实现:接口允许换数据库

| 维度 | agent-core 层 | coding-agent 层 |
|---|---|---|
| API 风格 | 异步 | 同步 |
| Entry 类型 | 11 种 | 9 种 |
| 存储 | `SessionStorage` 接口(可插拔) | 独立实现,直接操作 JSONL |
| 用途 | 通用框架层 | 编码 Agent 产品层 |

> [!important] 接口存在但 coding-agent 不复用
> coding-agent 的 SessionManager ==并未实现== agent-core 的 SessionStorage 接口——完全独立的实现,直接操作自己的 JSONL,复用了 agent-core 类型定义(如 `SessionEntry`)但没复用存储抽象。两套实现平行存在。
>
> 含义:① 你想做 Web 版 Pi Agent,可自己用 mysql 实现 `SessionStorage`,agent-core 其他逻辑不用改;② 但不能直接拿 coding-agent 的 SessionManager 套 agent-core 的 SessionStorage——签名不兼容。=="接口允许换数据库"落地路径是"各自实现"而非"统一继承"==。

## 八、总结

### 一条主线:会话存储的两个独立维度

| 维度 | 回答什么 | 一般做法 | Pi 的选择 |
|---|---|---|---|
| 存储介质 | 存哪里? | mysql 等数据库 | 本地 JSONL 文件(接口允许换) |
| 数据结构 | 长什么样? | 线性数组 | 树(Session Tree) |

==这两个维度可独立做选择==。设计持久化系统先问这两个问题再决定方案,不要粘成一团。

### Session Tree 的本质:用树形 + append-only 实现"不丢数据的回退"

- **为什么树?** 对话不是线性的——用户会回退、重试、分支
- **为什么 append-only?** 删了的数据找不回来,历史分支可能有价值
- **为什么认父不认子?** append-only 要求节点不可变,父节点不能维护 children 列表
- **为什么路径遍历?** LLM 只认线性 messages 数组,树形数据必须"压扁"

==这一连串设计选择是连贯的——每个都回应上一个带来的约束,最终形成自洽方案==。

### 三个可迁移的思路

1. **拆开"存哪里"和"长什么样"两个维度**。混在一起会让选择空间被压缩——你以为"用数据库就必须线性数组"或"用文件就必须 append-only",其实不然
2. **append-only 数据结构用于"撤销/回退/分支"场景**。不要删除旧数据,用 append-only + 指针定位(leafId)让历史完整保留。==代价是存储空间,但磁盘便宜、数据无价==
3. ==节点化状态变量,让回退天然正确==。Pi 把"切换模型""调整思考级别"也存成节点(ModelChangeEntry 等)而不是塞进全局状态对象。回退时状态变量自动回到当时样子——路径遍历只看当前路径变更,自动忽略被回退掉的变更
