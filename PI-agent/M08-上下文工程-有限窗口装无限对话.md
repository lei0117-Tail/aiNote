# M08 上下文工程 —— 让有限窗口装下无限对话

> [!abstract] 核心结论
> 上下文压缩只是冰山一角。Pi 在 ==输入、历史两个环节== 都布置防线,实现 4 种互补技巧:① 工具输出截断(单条太大)② 系统提示词组装(项目规范注入)③ Compaction(线性对话过长)④ 分支摘要(树状对话分支遗忘)。==没有银弹,只有层层兜底==。

承接 [[M07-事件驱动-Agent的神经系统]]——`agent_end` 后触发上下文检查,`transformContext` 在 `convertToLlm` 前执行。

---

## 一、问题:窗口是固定的,对话是增长的

```
一次会话送进 LLM 的内容
├── 系统提示词(工具说明、guidelines、pi 文档路径)
├── 项目上下文文件(CLAUDE.md / AGENTS.md,可能多层嵌套)
├── Skills 列表(每个 skill 一段描述)
├── 工具定义(每个工具的 JSON schema)
├── 对话历史(每轮 user/assistant/toolResult)
└── 当前轮的新输入
```

随便挑一项都可能爆炸:`npm install` stderr 十几 KB;`read` 5000 行源文件 80KB;`grep` 全仓库命中几百行;几十轮对话轻松破 100K token。而 LLM 窗口是硬上限——超了报错 `prompt is too long`。

> [!info] 上下文工程(Context Engineering)
> 在内容送入 LLM 之前,多层裁剪、过滤、压缩、组织,让有限窗口装下"对当前任务最有价值的信息"。

---

## 二、地图:两层防护

```
┌──────────────────────────────────────────────────────┐
│              输入侧(送进 LLM 之前)                    │
│  ① 工具输出截断 — bash/read/grep 结果按行/字节裁剪     │
│  ② 系统提示词组装 — 多层 CLAUDE.md 向上递归 + Skills 懒加载│
└──────────────────────────────────────────────────────┘
┌──────────────────────────────────────────────────────┐
│              历史侧(长对话管理)                       │
│  ③ Compaction — 阈值触发,旧消息变结构化摘要            │
│  ④ 分支摘要 — 切换会话树分支时给"被放弃分支"做摘要      │
└──────────────────────────────────────────────────────┘
```

| 层 | 解决问题 | 触发频率 |
|---|---|---|
| ① 工具输出截断 | 单次工具结果太大 | 每次工具调用 |
| ② 系统提示词组装 | 项目规范要进上下文,又不能让用户每次说 | 每轮 prompt |
| ③ Compaction | 长对话累积超窗口 | 阈值触发 |
| ④ 分支摘要 | 会话树分支跳转,旧分支不能丢 | 用户切换分支时 |

## 三、输入侧 ①:工具输出截断(truncateHead / truncateTail)

### 双重限制:行数 + 字节,先触者胜

源码 `truncate.ts:11-13`:
```
DEFAULT_MAX_LINES = 2000              行数上限
DEFAULT_MAX_BYTES = 50 * 1024         字节上限(50KB)
GREP_MAX_LINE_LENGTH = 500            grep 单行长度上限
```

任何工具输出按"最多 2000 行"或"最多 50KB"裁剪,哪个先触发用哪个。

> [!question] 为什么双限制?
> - 只限行数:单行可能极长(压缩 JS、minified CSS),3 行撑爆字节
> - 只限字节:50KB 源文件可能 200 行,按字节切可能把第 100 行切一半
> - ==双限制互相兜底——行数管"展示可读性",字节管"硬性体积"==

### 两种策略:truncateHead vs truncateTail

| 函数 | 保留哪段 | 用在哪 | 为什么 |
|---|---|---|---|
| `truncateHead` | 开头 | read 文件 | 头部通常是 import/类定义/接口签名,信息密度最高 |
| `truncateTail` | 末尾 | bash 输出 | 错误堆栈、最终结果都在末尾,末尾最有信号 |

bash 工具契约(`bash.ts:284`):"Output is truncated to last 2000 lines or 50KB"。"last" 是关键——保留末尾。

```js
// truncateTail 核心思路(truncate.ts:247-266)
function truncateTail(content, maxLines, maxBytes) {
    const lines = content.split("\n");
    const kept = [];  let bytes = 0;
    for (let i = lines.length - 1; i >= 0; i--) {        // 从末尾往回收集
        const lineBytes = byteLength(lines[i]) + 1;
        if (kept.length >= maxLines) break;
        if (bytes + lineBytes > maxBytes) break;
        kept.unshift(lines[i]);  bytes += lineBytes;     // 插头部保持原顺序
    }
    return kept.join("\n");
}
```

### 边界安全:UTF-8 多字节字符

字节级截断最阴险的 bug 是切坏多字节字符。emoji 😀 在 UTF-8 是 4 字节,在第 2 字节切一刀剩下两个字节变无效字符 `�`。Pi 用 `truncateStringToBytesFromEnd`(`truncate.ts:295`)——逐字符累加字节数,处理代理对(surrogate pair),4 字节 emoji 当成不可分割整体。`replaceUnpairedSurrogates` 处理输入本身损坏的情况。

> [!note] replaceUnpairedSurrogates 位置差异
> 此函数仅在 `agent` 包 `truncate.ts:82` 存在;`coding-agent` 包简化实现,直接用 `Buffer.byteLength + slice`,未保留该函数。

### 单行就超限:部分行兜底

第一行(最长行)单独超 maxBytes,不能返回空。取这行末尾 maxBytes 字节,设 `lastLinePartial:true`。bash 渲染:
```
[Showing last 49.5KB of line 1 (line is 92.3KB). Full output: /tmp/pi-bash-xxx.log]
```

### grep 的 500 字符规则

`truncateLine`(`truncate.ts:336`)把超长行截到 500 字符加 `... [truncated]`,避免压缩 JS 一行吃掉几千 token。

### 截断后的提示:逃生通道

bash 在输出末尾追加:
```
[Showing lines 6501-8500 of 8500. Full output: /tmp/pi-bash-xxx.log]
```

> [!tip] 逃生通道
> 这行字进 LLM 上下文——告诉模型"想看完整输出去 read 这个文件"。==默认截断省 token,需要时 LLM 自己拉完整内容==。

> [!info] 流式输出补充
> bash 是流式输出(stdout 一行一行吐,可能持续几分钟)。`OutputAccumulator` 类实时收集、控制内存、超限内容写临时文件——但最终截断仍走 `truncateTail`。流式累积是工程实现细节,非核心机制。

==双重限制 + 双向策略 + 边界安全 + 兜底逃生——Pi 工具输出截断的四件套==。

## 四、输入侧 ②:系统提示词动态组装

### 多级上下文文件:从当前目录向上递归

每个目录找 `AGENTS.md` 或 `CLAUDE.md`(大小写都试),从 `cwd` 向上递归到根,沿途所有规范文件合并。`resource-loader.ts:85-123` 的 `loadProjectContextFiles`。

```
/myorg
├── CLAUDE.md          ← 全组织规范(通用)
└── teams/teamA/projects/app1
    ├── CLAUDE.md      ← 项目规范(最具体)
    └── src/           ← cwd 在这里
```

在 `src/` 启动,向上找到 3 个 CLAUDE.md,按"从外到内"合并——祖先目录规范在前面(通用),项目目录规范在后面(具体)。查找顺序:

```
1. agentDir/CLAUDE.md   ← 全局(用户级 ~/.pi/)
2. 祖先目录/CLAUDE.md   ← 从 / 到 cwd 上一层
3. cwd/CLAUDE.md        ← 当前项目
```

### XML 包装:让 LLM 理解"这是一份项目指令"

```xml
<project_context>
  Project-specific instructions and guidelines:
  <project_instructions path="/myorg/CLAUDE.md">
    全组织规范:所有项目使用 TypeScript strict 模式...
  </project_instructions>
  <project_instructions path="/myorg/.../app1/CLAUDE.md">
    本项目使用 pnpm,测试用 vitest...
  </project_instructions>
</project_context>
```

> [!question] 为什么用 XML 不用 Markdown?
> - ==XML 边界明确==——`</project_instructions>` 是清晰结束标记,LLM 不会把规范和外部指令混淆
> - 带 path 属性——LLM 看到内容来自哪个文件,能区分优先级

### Skills 懒加载:列表进 prompt,内容按需读

每个 skill 是 `SKILL.md`,可能几千字。全文塞进系统提示词 token 开销巨大且大部分用不上。`formatSkillsForPrompt`(`skills.ts:335-361`)只放轻量清单:

```
传统方式(推模式)              Pi 的方式(拉模式)
系统提示词 ←─ 全文塞进           系统提示词 ←─ 只放清单
                                  │ LLM 看清单,判断需要哪个
                                  ▼ LLM 主动调 read 工具
                                  │ SKILL.md 全文进入后续上下文
```

```xml
<available_skills>
  <skill>
    <name>test-setup</name>
    <description>How to run tests for this project</description>
    <location>/path/to/skills/test-setup/SKILL.md</location>
  </skill>
</available_skills>
```

清单顶上指令:"Use the read tool to load a skill's file when the task matches its description"——==用时才付 token,不用不付==。

| 方案 | Token 开销 | 信息密度 |
|---|---|---|
| 全文塞 | 10 skill × 2000 字 ≈ 50K token | 大部分无关 |
| 懒加载 | 10 skill × 4 行 ≈ 500 token | 精准命中时才展开 |

### 系统提示词完整骨架

```
1. 角色定位    "You are an expert coding assistant..."
2. 工具列表    "- read: Read a file\n- bash: Execute..."
3. 通用 guidelines
4. Pi 文档路径(让 LLM 能 read 自身文档)
5. [可选] appendSystemPrompt
6. <project_context>... CLAUDE.md ...</project_context>
7. <available_skills>... Skills 清单 ...</available_skills>
8. Current date: 2026-07-03
9. Current working directory: /path/to/cwd
```

> [!info] 末尾的 date 和 cwd 是基本元数据
> LLM 需知道"今天哪天"(处理"昨天""上周"相对时间)、"我在哪个目录"(处理相对路径)。

## 五、历史侧 ③:Compaction(联动第9章)

长对话终究超窗口。Compaction 是核心压缩算法——把旧消息变结构化摘要替代原始消息。详见 [[M09-上下文压缩-对话太长怎么办]]。

关键事实:Compaction 生成的 `CompactionSummaryMessage` 会出现在后续对话的 `context.messages` 里作为新上下文。

## 六、历史侧 ④:分支摘要(Branch Summarization)

Compaction 解决"线性对话过长"。但 Pi 有会话树(第10章)——对话是一棵树,用户可从历史节点分叉新对话。带来新问题:用户切换分支时,旧分支探索成果不能丢。

### 问题:分支跳转后,旧分支内容怎么处理?

```
对话树:
    root → [探索方案 A] → [A 的实现] → leaf_1
用户从 root 重新分叉探索方案 B:
    root → [探索方案 A] → [A 的实现] → leaf_1(旧叶子,被"放弃")
         → [探索方案 B] → leaf_2(用户现在在这里)
```

切换后 LLM 看到的是 root→leaf_2 路径,完全不知道 leaf_1 分支探索过什么。如果那分支有重要发现("试过方案 A 但行不通,因为 X、Y、Z"),LLM 失忆了。

### LCA 算法:找"分叉点"

`collectEntriesForBranchSummary`(`branch-summarization.ts:67-96`)三步:
1. 把旧路径(root→leaf_1)和新路径(root→leaf_2)都拿出来
2. 在新路径从后往前找,第一个也在旧路径里的节点 = LCA(分叉点)
3. 从 leaf_1 向上爬到 LCA(不含),沿途收集的就是"被放弃的分支"

### 摘要生成:复用 Compaction 工具

`generateBranchSummary`(`branch-summarization.ts:199-261`)复用 Compaction 底层工具:`convertToLlm`/`serializeConversation`/`SUMMARIZATION_SYSTEM_PROMPT`。==两套摘要机制共享同一套底层管道,只是 prompt 不同==。

### 与 Compaction 的关键差异

**差异 1:上下文前言不同**
```ts
const BRANCH_SUMMARY_PREAMBLE =
    `The user explored a different conversation branch before returning here.\n
     Summary of that exploration:\n\n`;
// LLM 知道这不是"主线历史",而是"另一条线的探索记录",对待更轻量
```

**差异 2:maxTokens 更小**

Compaction 是 `min(0.8 × reserveTokens, model.maxTokens)`(可能上万 token);Branch Summary ==写死 2048==(`branch-summarization.ts:234`)。

> [!question] 为什么分支摘要要求更精简?
> 它只是辅助上下文,主线还是新分支。新分支自己也需要 token 预算,==分支摘要不能喧宾夺主==。

### Compaction vs Branch Summarization 对照

| 维度 | Compaction | Branch Summarization |
|---|---|---|
| 触发 | 阈值(contextTokens > window - reserve) | 用户切换会话树分支 |
| 目的 | 防止窗口溢出 | 保留被放弃分支的探索成果 |
| 切割 | findCutPoint 算法(向后累积) | LCA 算法(找分叉点) |
| 保留区 | 最近 N tokens 的消息 | 新分支路径(完全保留) |
| 压缩区 | 旧消息(被摘要替代) | 旧分支整条路径 |
| maxTokens | min(0.8×reserve, model.maxTokens) | 2048(固定,更精简) |
| 前言语义 | "history compacted" | "explored a different branch" |
| 共存 | 一个对话可能多次 compaction | 一个分支跳转产生一条分支摘要 |

==两者互补——Compaction 处理"线性对话长度",Branch Summarization 处理"树状对话分支遗忘"==。

## 七、全景链路:一次工具调用经过的所有上下文处理

```
用户输入 "修复 auth.ts 的 bug"
    │
[1] 系统提示词组装(§四):buildSystemPrompt() 找 CLAUDE.md 递归+Skills 懒加载+工具列表+guidelines+date/cwd
[2] 用户消息进入 context.messages(第6章)
[3] Agent Loop 开始(第3章五步管道)
[4] LLM 返回 toolCall: read("auth.ts")
[5] 执行工具 read auth.ts
[6] 工具输出截断(§三):truncateHead(read) 2000行/50KB 双限制+UTF-8 边界安全
[7] 工具结果进入 context.messages(第5章)
    ...循环...
[8] agent_end 事件触发(第7章)
[9] 检查 shouldCompact?(§五/第9章)
    ├── 否 → 等下一轮
    └── 是 → 执行 Compaction:findCutPoint→generateSummary→CompactionSummaryMessage→写入 Session Tree
    用户切换分支?
[10] Branch Summarization(§六):collectEntriesForBranchSummary(LCA)→generateBranchSummary→BranchSummaryMessage
```

四层都是"对 LLM 看到的东西"的一次塑形:§三 控制单条体积;§四 控制提示词内容;§五 控制长对话总长;§六 控制多分支信息保留。==组合成一道"漏斗",最后送进 LLM 的才是"对当前任务最有价值的信息"==。

## 八、设计精华:三个值得带走的思路

### 1. 多层防护:没有银弹,只有层层兜底

每层只解决自己擅长的问题,互不替代。==你可以把 Compaction 调得很激进,但单条工具输出仍需 truncate==——80KB read 结果连一轮都撑不过。反过来也一样。

> [!warning] 新手常犯错误
> "找到一招就用到底"(比如只靠 LLM 自己处理超长输入),结果遇具体场景就炸。Pi 方案:每层做最朴素、最可靠的事,多层叠加形成完整防线。

### 2. 加法 + 减法:上下文工程的双向操作

- §三 减法——把太大的变小
- §四 加法——主动加入项目规范和 Skills
- §五~§六 裁剪同时做加法——加入结构化摘要、加入被放弃分支探索成果

> [!important] 上下文工程不是单纯"压缩",而是"塑形"
> ==在体积约束下,让信息更准确、更有结构、更易理解==。同等 token,结构化的信息密度更高。直接拼 50 轮原始文本扔给 LLM,效果远不如"结构化摘要 + 近期消息"。

Pi 三处体现:Compaction 6 section 模板;Branch Summary 5 section 模板;系统提示词 XML 标签。==结构化是上下文工程的杠杆——用一点点 prompt 工程撬动 LLM 对信息理解的巨大提升==。

### 3. 工具调用 = 按需上下文加载

Skills 懒加载揭示更深设计模式——用工具调用做按需上下文加载。

| 维度 | 推模式(传统) | 拉模式(Pi Skills) |
|---|---|---|
| Token 开销 | 全部预付 | 用时才付 |
| 信息密度 | 大部分无关 | 精准命中 |
| LLM 主动性 | 被动接收 | 主动选择 |
| 适用场景 | 必须知道的信息 | 可能用到的信息 |

> [!success] 核心洞察
> 当 LLM 有工具调用能力时,=="工具"本身就是上下文工程的载体==——不需把所有可能用到的信息塞进 prompt,让 LLM 用工具按需取。Claude Code 的 Skills、Cursor 的 docs、Cline 的 context files 本质都是同一套机制。Pi 实现最干净:XML 清单 + read 工具 + 路径解析约定,三行字定义全部契约。
